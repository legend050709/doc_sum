# 需求
"代码的根目录下存在以下的几大目录，分别是src、app、tools和include；

将src目录下的代码，编译为动态库以及静态库，静态库和动态库的生成过程中，还需要依赖外部目录下的指定的几个静态库以及动态库；
另外补充一下，src存在多个子目录，子目录下的c文件会引用和src平行的include中的头文件。

和src平行的app目录，app目录下存在多个测试程序，这些测试程序对应的c文件代码使用上面编译生成的静态库，以及app平行的include的头文件，来进行编译生成多个可执行的测试程序"。

tools目录下存在多个子目录，每个子目录都是一个工具程序。

基于上诉的需求，编译app、tools以及src下的Makefile，以及外层和src/app/tools平行的总的Makefile，编写时需要考虑后续的扩展性。

## 场景
比如，编写 RDMA 通信的中间件，中间件以库的形式提供给业务程序使用。
RDMA中间件又使用了 DPDK中的库。

# 分析
## 目录结构
```bash
project/
├── Makefile              # 总控Makefile
├── include/              # 公共头文件
├── src/                 # 库源码
│   ├── module1/        # 子模块1
│   │   ├── module1.c  
│   ├── module2/        # 子模块2
│   │   ├── module2.c

├── app/                 # 测试程序
│   ├── app1.c           # app1
│   ├── app2.c           # app2
│   └── Makefile         # 应用构建规则
├── tools/               # 工具目录
│   ├── Makefile         # tools的总控 Makefile
│   ├── tool1/           # 工具1
```

## 关键设计要点

**（1）模块化分层**
- 总控Makefile负责全局配置
- src/Makefile专注库构建
- app/Makefile专注应用构建
- tool/Makefile 专注工具构建

 **(2) 自动发现机制**
```Makefile
# 自动递归查找所有.c文件（库）， 当前目录下存在子目录，子目录中的.c文件也会被查找到
SRCS := $(shell find . -type f -name '*.c')

# 自动发现所有测试程序（应用）
APP_SRCS := $(wildcard *.c)
```

**(3)路径管理策略** 
构建产物统一存放在`build`目录下：
```bash
build/
├── lib/    # 库文件
├── app/    # app可执行文件
└── obj/    # 中间文件
└── tool/   # tools可执行文件

# 分离静态库和动态库的中间文件
$(BUILD_DIR)/obj/src/static/  # 静态库目标文件
$(BUILD_DIR)/obj/src/shared/  # 动态库目标文件
```

**(4)扩展性保障**
    
- 添加新库模块：只需在src下新建子目录和源文件
- 添加新测试程序：只需在app下新建.c文件
- 添加新工具程序：只需在tools下新建子目录
- 修改编译选项：只需修改总控Makefile的全局变量
- 扩展外部库：修改`src`下的`Makefile`的`EXT_STATIC_LIB_NAMES`和`EXT_DYNAMIC_LIB_NAMES`变量


# 实现
## 总控 Makefile
```bash
export CC = gcc
export CFLAGS = -std=gnu99 -g -Wall -O3 -mssse3 -flto -I${PWD}/include

export BUILD_DIR = ${PWD}/build
export BUILD_LIB_DIR = ${PWD}/build/lib
export OUTPUT_LIB_NAME := mylibaaa

.PHONY: all lib app clean

all: lib app tools

lib:
	@mkdir -p $(BUILD_DIR)/lib
	@$(MAKE) -C src

# 此中 `app: lib` 是为了防止 `make -j N` 多线程编译出错。因为app中的Makefile依赖src中Makefile编译生成的库。
app: lib
	@mkdir -p $(BUILD_DIR)/app
	@$(MAKE) -C app

tools: lib
	@mkdir -p $(BUILD_DIR)/tools
	@$(MAKE) -C tools

clean:
	@$(MAKE) -C src clean
	@$(MAKE) -C app clean
	@$(MAKE) -C tools clean
	@rm -rf $(BUILD_DIR)
```
## src下 Makefile
```bash
INCLUDES = -I$(CURDIR) -I$(shell pkg-config --variable=includedir libdpdk)

AR := gcc-ar
SRC_FILES := $(shell find . -type f -name '*.c')
OBJ_DIR   := $(BUILD_DIR)/obj/src

STATIC_OBJS := $(addprefix $(OBJ_DIR)/static/,$(SRC_FILES:.c=.o))
SHARED_OBJS := $(addprefix $(OBJ_DIR)/shared/,$(SRC_FILES:.c=.o))

STATIC_LIB  := $(BUILD_DIR)/lib/lib$(OUTPUT_LIB_NAME).a
STATIC_TMP_LIB  := $(BUILD_DIR)/lib/lib$(OUTPUT_LIB_NAME)_tmp.a
DYNAMIC_LIB := $(BUILD_DIR)/lib/lib$(OUTPUT_LIB_NAME).so

EXT_STATIC_LIB_DIRS   := $(shell pkg-config --variable=libdir libdpdk)
EXT_STATIC_LIB_NAMES  := librte_mempool.a librte_ring.a librte_eal.a librte_telemetry.a librte_kvargs.a librte_mempool_ring.a
EXT_STATIC_LIB_FULL := $(foreach lib,$(EXT_STATIC_LIB_NAMES),$(wildcard $(EXT_STATIC_LIB_DIRS)/$(lib)))
EXT_STATIC_LINK := -Wl,-Bstatic -Wl,--whole-archive $(EXT_STATIC_LIB_FULL) -Wl,--no-whole-archive
ifeq ($(words $(EXT_STATIC_LIB_FULL)),0)
$(error Missing static libraries: $(EXT_STATIC_LIBS))
endif

EXT_DYNAMIC_LIB_NAMES := -libverbs -lpthread -ldl -lnuma
EXT_DYNAMIC_LINK := -Wl,-Bdynamic $(EXT_DYNAMIC_LIB_NAMES)

MRI_FILE=$(BUILD_DIR)/lib/libkucl.mri

.INTERMEDIATE: $(STATIC_TMP_LIB)

.PHONY: all clean

all: $(STATIC_LIB) $(DYNAMIC_LIB)

$(STATIC_TMP_LIB): $(STATIC_OBJS)
	@echo "Merging static libraries..."
	@$(AR) rcs $@ $^

$(STATIC_LIB): $(STATIC_TMP_LIB)
	echo "AR $(STATIC_LIB) by MRI_FILE script..."
	echo create $(STATIC_LIB) > $(MRI_FILE)
	echo addlib $(STATIC_TMP_LIB) >> $(MRI_FILE)
	for i in $(EXT_STATIC_LIB_FULL); do \
    	echo addlib $$i >> $(MRI_FILE); \
	done
	echo save >> $(MRI_FILE)
	$(AR) -Ms < $(MRI_FILE)
	rm -rf $(MRI_FILE)

$(DYNAMIC_LIB): $(SHARED_OBJS)
	@echo "Linking shared libraries..."
	@$(CC) -shared -o $@ $^ $(EXT_STATIC_LINK) $(EXT_DYNAMIC_LINK)

$(OBJ_DIR)/static/%.o: %.c
	@mkdir -p $(dir $@)
	@$(CC) $(CFLAGS) $(INCLUDES) -c $< -o $@

$(OBJ_DIR)/shared/%.o: %.c
	@mkdir -p $(dir $@)
	@$(CC) $(CFLAGS) $(INCLUDES) -fPIC -c $< -o $@

clean:
	@rm -rf $(OBJ_DIR) $(STATIC_LIB) $(DYNAMIC_LIB)
```

## 说明
### `APP_TARGETS := $(addprefix $(BUILD_DIR)/bin/,$(APP_SRCS:.c=))`

- **（1）`APP_TARGETS`**: 
这是一个变量，用于存储应用程序的目标文件路径。

- **（2）`$(APP_SRCS:.c=)`**: 
这是一个模式替换的语法。它会将 `APP_SRCS` 变量中所有以 `.c` 结尾的源文件名去掉 `.c` 后缀，生成一个没有后缀的文件名列表。例如，如果 `APP_SRCS` 包含 `main.c` 和 `utils.c`，那么这个部分将生成 `main` 和 `utils`。

- **（3）`$(addprefix $(BUILD_DIR)/bin/, ...)`**: 
`addprefix` 函数将 `$(BUILD_DIR)/bin/` 这个前缀添加到前面生成的每个文件名上。假设 `BUILD_DIR` 是 `build`，那么最终的 `APP_TARGETS` 将会是 `build/bin/main` 和 `build/bin/utils`。

### `STATIC_OBJS := $(addprefix $(OBJ_DIR)/static/,$(SRC_FILES:.c=.o))`

- **（1）`STATIC_OBJS`**: 
这是一个变量，用于存储静态对象文件的路径。

- **（2）`$(SRC_FILES:.c=.o)`**:
这个模式替换语法将 `SRC_FILES` 变量中所有以 `.c` 结尾的源文件名替换为以 `.o` 结尾的对象文件名。例如，如果 `SRC_FILES` 包含 `main.c` 和 `utils.c`，那么这个部分将生成 `main.o` 和 `utils.o`。

- **（3）`$(addprefix $(OBJ_DIR)/static/, ...)`**: 
`addprefix` 函数将 `$(OBJ_DIR)/static/` 这个前缀添加到前面生成的每个对象文件名上。假设 `OBJ_DIR` 是 `obj`，那么最终的 `STATIC_OBJS` 将会是 `obj/static/main.o` 和 `obj/static/utils.o`。



### `$<`
- **含义**: 代表当前规则的第一个依赖文件。
- **用法**: 在规则中，`$<` 通常用于指定源文件。例如，在 `$(BUILD_DIR)/bin/%: %.c` 规则中，`$<` 将代表与目标文件对应的 `.c` 源文件。

### `$@`
- **含义**: 代表当前规则的目标文件。
- **用法**: 在规则中，`$@` 用于引用当前正在生成的目标。例如，在 `$(DYNAMIC_LIB): $(SHARED_OBJS)` 规则中，`$@` 将代表 `$(DYNAMIC_LIB)` 的值（即最终生成的动态库的文件名）。

### `$^`
- **含义**: 代表当前规则的所有的依赖文件（不重复）。
- **用法**: 在规则中，`$^` 用于引用所有的依赖文件的列表。例如，在 `$(DYNAMIC_LIB): $(SHARED_OBJS)` 规则中，`$^` 将代表所有的共享对象文件（`$(SHARED_OBJS)`），并且如果某些对象文件在列表中重复出现，它们只会列出一次。


### `ALL_OBJS := $(patsubst ./%.c,$(OBJ_DIR)/%.o,$(SRC_FILES))`
```bash
$(patsubst pattern,replacement,text)

此中：
ALL_OBJS := $(patsubst ./%.c,$(OBJ_DIR)/%.o,$(SRC_FILES))
```

这是 Makefile 的**模式替换函数**，包含三个部分：
```bash
1. `./%.c` - 匹配模式
2. `$(OBJ_DIR)/%.o` - 替换模式
3. `$(SRC_FILES)` - 要处理的文本列表


函数会查找所有匹配 `./%.c` 格式的文件名：
- `./` 匹配字面目录
- `%` 匹配任意字符串（包括子目录路径）
- `.c` 匹配文件扩展名

对于每个匹配的文件，将 `./%.c` 替换为 `$(OBJ_DIR)/%.o`：
- `./` → `$(OBJ_DIR)/`
- `%` → 保持不变（保留路径部分）
- `.c` → `.o`

范例：
原始路径 | 替换结果 
------------------------------- 
./main.c → build/obj/main.o 
./utils/file.c → build/obj/utils/file.o 
./network/http.c → build/obj/network/http.o
```


# 其他
## 编译静态库时候，如果代码中使用了外部的静态库或者动态库的函数，需要指定外部库的路径或者名称吗？

### 分析
用户可能混淆了编译和链接阶段的不同需求。

编译静态库时，只要存在的依赖的其他的库的函数的头文件，就可以编译`.o`文件成功，进而通过`ar`归档命令，就可以将`.o`文件归档为静态库文件；只有链接时才需要处理依赖的其他的库文件。。

静态库（.a文件）其实是一堆对象文件（.o）的归档，并不涉及链接过程。
所以在编译静态库时，只需要确保源代码能够找到外部库函数对应的头文件，正确编译生成.o文件，而不需要处理外部库的链接。

==链接外部库的工作应该是在最终生成可执行文件或动态库的时候进行的==。
但用户的问题中提到他们的代码依赖了外部库，这时候在编译静态库的源代码时，必须包含这些外部库的头文件，否则编译会失败。

因此，在编译阶段需要指定外部库的头文件路径，使用编译器的`-I`选项。例如，在`Makefile`中设置`CFLAGS += -I/path/to/include`。这样编译器在编译每个`.c`文件时，能够找到所需的头文件。

接下来是关于链接的问题。当用户将静态库（如`libmylib.a`）与其他代码一起链接生成可执行文件时，这时候需要指定所有依赖的外部库，包括静态库和动态库。这时候需要用到链接器的`-L`选项指定库路径，`-l`指定库名称，或者直接给出静态库的路径。例如，链接时需要`-lfoo` `-lbar`，并确保路径正确，否则会报找不到符号的错误。

### 流程
对外部库的处理需要分为两个阶段，以下是分步说明：
（1）生成静态库：编译以及归档生成
（2）程序使用静态库，即链接静态库。

#### 静态库的编译阶段（生成静态库 .a 文件）
==编译静态库，其实也分为2个阶段，一个是生成`.o`文件，一个是将`.o`文件归档(archive), 不涉及到`.o`文件的链接==。

而在编译.o文件的时候，只需处理头文件依赖；因为不涉及链接，也就无需链接外部的库文件。

**(1)需要指定的内容：**
头文件路径：（通过 `-I` 指定） 确保编译器能找到外部库的头文件（`.h` 文件）。

 **(2)不需要指定的内容：**
- 外部静态库（`.a`）或动态库（`.so`）的路径
- 外部库的名称（如 `-lfoo`）

#### 静态库的链接阶段（生成最终可执行文件）
链接生成可执行文件的时候，需要处理库文件依赖，此时需指定所有外部库的路径和名称。

**（1）需要指定的内容：**
- 库文件路径（通过 `-L` 指定）
- 库名称（通过 `-l` 指定动态库，或直接写静态库全名）

 **(2) 完整范例 **
 
```bash
# 编译配置
CC = gcc
CFLAGS = -I./include -I/path/to/external_lib/include
LDFLAGS = -L/path/to/external_lib/lib
LDLIBS = -lfoo -lbar /path/to/external_lib/libbaz.a

# 生成静态库
OBJS = mylib.o
libmylib.a: $(OBJS)
    ar rcs $@ $^

# 编译目标文件
%.o: %.c
    $(CC) $(CFLAGS) -c $< -o $@

# 生成可执行文件
app: main.o libmylib.a
    $(CC) $^ -o $@ $(LDFLAGS) $(LDLIBS)

# 清理
clean:
    rm -f *.o libmylib.a app
```


#### 小结

|阶段|需要指定的内容|不需要指定的内容|
|---|---|---|
|编译静态库|外部库的头文件路径（`-I`）|外部库的路径或名称|
|链接可执行文件|外部库路径（`-L`）和名称（`-l` 或全路径）|无|


### 小结
区分：`.o`文件的归档(archive: ar)和 `.o`文件的链接（link）;
==静态库（.a文件）其实是一堆对象文件（.o）的归档，并不涉及链接过程==。
**编译静态库时，只要存在的依赖的其他的库的函数的头文件，就可以编译`.o`文件成功，进而通过`ar`归档命令，就可以将`.o`文件归档为静态库文件**；只有链接时才需要处理依赖的其他的库文件。

==静态库不会自动包含其他静态库的代码==，最终链接时必须同时指定所有依赖库。
如果静态库A依赖静态库B，那么在生成静态库A的时候，是否需要将B的内容打包进去？
答案是否定的，静态库只是对象文件的集合，不会自动包含其他静态库的内容。在最终链接时，必须同时链接A和B，否则会缺失符号。这一点需要特别强调，避免用户以为只需要链接主静态库即可。

但是，可以通过`ar`命令，将多个静态库归档为一个静态库文件（其实就是==将多个静态库的`.o`文件都统统归档到一个静态库中==），这样在链接的时候，只用这一个静态库就可以了，就不需要链接多个静态库了。

## 编译动态库时候，如果代码中使用了外部的静态库或者动态库的函数，需要指定外部库的路径或者名称吗？

### 流程
（1）编译动态库
通常分为两个阶段：编译阶段（生成目标文件）和链接阶段（将目标文件打包成动态库）。


（2）动态库的链接阶段
程序使用动态库，就一个阶段：即链接动态库，生成最终可执行文件。

#### 编译动态动态库
##### 编译阶段（生成目标文件 `.o`）
**编译阶段（生成目标文件）**：
只需处理头文件依赖，无需指定库路径或名称。

**（1）需要指定头文件搜索路径**
通过 `-I` 选项， 确保编译器能找到外部库的头文件（`.h` 文件）。


比如：
```bash
gcc -fPIC -I/path/to/external_lib/include -c mylib.c -o mylib.o
```

##### 链接阶段（生成动态库 `.so`）
**链接阶段（将目标文件打包成动态库）**：

需根据依赖类型区别处理：
**（1）依赖动态库（`.so`）**
- 推荐不直接链接：
==保持动态库的运行时依赖==特性， 动态库的依赖会在运行时通过动态链接器（`ld.so`）自动解析。

- 指定依赖关系（可选）
用于显式声明依赖：
```bash
gcc -shared -o libmylib.so mylib.o \
    -Wl,-rpath,/path/to/external_lib/lib \
    -L/path/to/external_lib/lib -lfoo

说明：
`-L`：指定链接时的库搜索路径
`-lfoo`：指定依赖的动态库名称
`-Wl,-rpath`：指定运行时的库搜索路径（可选）
```


**（2）依赖静态库（`.a`）**
- 必须显式链接
静态库代码会被合并到动态库中：
```bash
# 直接指定静态库的完整路径
gcc -shared -o libmylib.so mylib.o /path/to/external_lib/libbar.a

# 或使用 `-L` + `-l` 组合
gcc -shared -o libmylib.so mylib.o -L/path/to/external_lib -lbar
```
对于静态库，链接时需要将静态库的路径和名称指定给链接器，使用`-L`指定路径，`-l`指定库名，或者直接使用库文件的绝对路径。


**（3）范例 **
```bash
# 编译动态库（依赖静态库 libbar.a 和动态库 libfoo.so）
CC = gcc
CFLAGS = -fPIC -I./include -I/path/to/external_lib/include
LDFLAGS = -shared
LIBS = -L/path/to/external_lib -lfoo /path/to/external_lib/libbar.a

all: libmylib.so

libmylib.so: mylib.o
	$(CC) $(LDFLAGS) -o $@ $^ $(LIBS)

mylib.o: mylib.c
	$(CC) $(CFLAGS) -c $< -o $@

clean:
	rm -f *.o *.so

```

**（4）小结 **

|依赖类型|需要指定的内容|是否合并到动态库|
|---|---|---|
|动态库|可选：`-L` 路径 + `-l` 名称（仅声明依赖）|否|
|静态库|必须：完整路径或 `-L` + `-l`|是|


#### 动态库的链接阶段（生成最终可执行文件）

生成可执行文件的过程中，使用了动态库，则通过 `-L`指定路径，`-l`指定库名，来指定具体的动态库。

### 静态库的编译和动态库的编译的区分
（1）静态库
编译生成静态库的过程中，不涉及到链接，只有编译生成对象文件，和对象文件的归档，因此不需要指定依赖的外部的静态库以及动态库；
后续在生成可执行的时候，需要指定静态库，还有静态库依赖的其他的静态库，以及动态库。

（2）动态库
编译生成动态库的过程中，涉及到编译生成对象文件，以及链接对象文件生成动态库。
如果依赖其他的静态库，那么在链接生成动态库的过程中，必须指定外部静态库的路径。
如果依赖其他的动态库，其实不需要指定动态库的路径，因为动态库的依赖会在运行时通过动态链接器（`ld.so`）自动解析；当然也可以指定依赖的外部动态库，只是做一个说明依赖关系的作用。

### 动态库对外暴漏的符号
生成动态库，还需要考虑符号可见性的问题。
动态库在链接时可能需要控制哪些符号暴露出来，==以避免与其他库的符号冲突==，
可以使用`-fvisibility=hidden`和显式导出符号，也可以使用版本脚本`-Wl,--version-script=`来指定哪些符号对外暴漏。

#### 编译选项：`-fPIC`
`-fPIC`代表生成位置无关代码（Position Independent Code）。

**（1）背景**
动态库需要在不同的进程中被加载到不同的内存地址，然后为了避免因绝对地址冲突导致段错误（Segmentation Fault），因此它们的代码必须能够在不修改的情况下在任何地址运行。这时候`-fPIC`就起作用了，它确保**编译器生成使用相对地址而不是绝对地址的代码**。

**（2）作用**
核心功能：
- 生成不依赖绝对地址的代码，确保代码段（`.text`）和数据段（`.data`/`.bss`）可以加载到任意内存地址。
- 通过 **全局偏移表（GOT）** 和 **过程链接表（PLT）** 实现间接寻址

具体的细节：
- 代码段：使用相对偏移（如 `call printf@PLT`）代替绝对地址
- 数据段：通过 `RIP` 相对寻址（x86_64）或 `GOT` 访问全局变量
- 重定位：减少运行时重定位次数，提高性能

**（3）作用阶段**：
编译阶段（生成目标文件 `.o` 时）

**(4) 范例**：
```bash
# 编译目标文件时必须使用 -fPIC
gcc -fPIC -c mylib.c -o mylib.o
```

#### 链接选项：`-shared`
**（1）介绍**
`-shared`选项，这个选项告诉编译器生成一个共享库（动态库）而不是可执行文件。共享库的文件扩展名通常是`.so`（在Linux）或`.dll`（在Windows）。
使用`-shared`时，链接器会处理所有的目标文件，并生成适合动态链接的库文件，其中包含符号表和重定位信息，以便在运行时被正确加载和链接。

**（2）作用**
核心功能：
- 指示链接器生成动态链接库（`.so`）而非可执行文件
- 生成动态库的符号表和重定位信息

技术细节：
- 输出文件格式为 `ET_DYN`（动态库类型）
- 添加 `.dynamic` 段，包含动态链接元数据
- 隐式设置 `-pie`（Position Independent Executable）特性

为何必须：
- 未使用 `-shared` 会默认生成可执行文件格式（`ET_EXEC`）
- 动态库需要特殊的段布局以支持运行时加载

**(3) 作用阶段**：
链接阶段（将目标文件链接为动态库）

**(4) 范例**：
```bash
# 链接时必须使用 -shared
gcc -shared mylib.o -o libmylib.so
```

##### `-fPIC` 和 `-shared`
`-fPIC`主要用于编译阶段，确保每个目标文件（.o）是位置无关的；而`-shared`则是在链接阶段，将这些目标文件合并成动态库。
因此，通常在编译动态库时，每个源文件都需要用`-fPIC`编译成位置无关的目标文件，然后再用`-shared`选项链接这些目标文件生成最终的`.so`文件。

##### 能否省略 `-fPIC`？
- **错误现象**：
```bash
/usr/bin/ld: mylib.o: relocation R_X86_64_PC32 against symbol `global_var' can not be used when making a shared object; recompile with -fPIC
```

- **原因**：目标文件未使用 `-fPIC` 编译，包含绝对地址引用
- **解决方案**：重新用 `-fPIC` 编译所有目标文件

##### 能否省略 `-shared`？

- **结果**：生成可执行文件而非动态库
- **验证**：使用 `file` 命令检查文件类型：

```bash
file libmylib.so
# 正确输出：ELF 64-bit LSB shared object, x86-64...
# 错误输出：ELF 64-bit LSB executable, x86-64...
```

##### 动态库能否链接静态库
- **可以**，如下所示：
```bash
# 链接静态库到动态库（libstatic.a 的代码会合并到 libmylib.so 中）
gcc -shared mylib.o /path/to/libstatic.a -o libmylib.so
```

- **限制**：静态库必须用 `-fPIC` 编译，否则可能引发链接错误。

## 编译器优化技术：`lto`

### 介绍
LTO（Link Time Optimization，**链接时优化**）顾名思义，就是在链接的时候，继续做一系列的优化，因此 LTO 是一种在链接阶段进行优化的技术。
**传统的编译过程（.c生成.o）中，编译器仅能对单个编译单元进行优化。即：编译器一次只能看到一个编译单元，因此没法跨文件范围做优化(如内联)**。

LTO 允许编译器看到跨编译单元的代码，从而进行更复杂和更有效的优化。LTO 可以提高程序的性能、缩减代码体积、提高代码安全性。

### 原理

![](attachments/Pasted%20image%2020250419230818.png)
编译器的优化器是以IR（Intermediate representation/中间表示）为输入，因此编译器在链接时优化，需要在编译过程中每个源文件(.c文件)生成的不再是真正的对象文件(.o文件)，而是"LTO对象文件"，这些文件中存储的不是二进制代码，而是编译器生成的`IR`。
链接时，编译器会将所有"LTO对象文件"合并到一起，合并后生成的巨大`IR文件`包含了所有源代码信息，这样就能跨文件对所有源代码（合并后的IR文件）进行集中的分析和优化，并生成一个真正的二进制文件，链接并得到可执行文件。
> 注：在链接时，当链接器发现这个文件是IR的表达（比如是llvm的bitcode格式的文件），就会将这些bitcode都读到内存里，等所有bitcode文件都读进去之后，才真正开始执行链接的工作。

因为编译器能够一次性看到所有源代码的信息，所以它做的分析具有更高的确定性和准确性，能够实施的优化也要多得多。

但在使用LTO优化大型的应用程序的时候，“链接”阶段将所有"LTO对象文件"合并成一个IR文件并生成的单个二进制文件可能非常庞大，这给系统虚拟内存造成很大压力，导致频繁内存换页，最终影响编译、链接的效率，甚至出现out of memory错误。 实际上，GCC编译器在LTO阶段首先会将所有文件中的符号表（symbol table）信息和调用图（call graph）信息合并到一起，这样不仅能跨文件对所有的函数进行全局的分析，而且内存压力也较小。WPA（whole program analysis, 全局分析）阶段会确定具体的优化策略，并依据优化策略将所有的"LTO对象文件"合并成一或多个IR文件。

![](attachments/Pasted%20image%2020250419230641.png)

这些IR文件再次并发经过优化器优化后，生成真正的二进制对象文件并传递给真正的链接器进行链接，最后得到可执行文件
![](attachments/Pasted%20image%2020250419230707.png)


==简单理解，就是把自己工程里的所有代码，都include到同一个头文件里，再执行编译，带来的效果就是可以更彻底地让编译去除一些DeadCode和配合PGO更好地调整指令==。

### 作用
#### 性能提升
LTO 可以通过以下方式提高程序的性能：
**内联函数**：将频繁调用的函数内联到调用点，可以减少函数调用的开销。
**函数重定位**：将函数的代码移动到更合适的位置，可以减少函数调用的距离。
**代码融合**：将多个代码块合并为一个代码块，可以减少代码的执行次数。
**数据流分析**：通过分析数据流，可以消除不必要的代码。

#### 代码体积缩减
LTO 可以通过以下方式缩减代码体积：
- **函数内联**：将频繁调用的函数内联到调用点，可以减少函数代码的体积。
- **代码删除**：通过分析数据流，可以消除不必要的代码。
- **代码融合**：将多个代码块合并为一个代码块，可以减少代码的体积。

#### 代码安全性提高
LTO 可以通过以下方式提高代码安全性：
- **函数内联**：将频繁调用的函数内联到调用点，可以减少函数调用带来的安全风险。
- **代码删除**：通过分析数据流，可以消除不必要的代码，从而减少代码中的安全漏洞。

### LTO 的使用
LTO 通常在生产环境中使用，以提高程序的性能和安全性。
LTO 可以通过编译器的**编译选项**来启用。例如，在 GCC 中，可以使用 `-flto` 选项来启用 LTO。

#### 编译静态库使用`lto`
##### 分析
首先，LTO（链接时优化）通常在链接阶段进行，但静态库本身就是目标文件的集合，还没有被链接。那么，在编译静态库时使用LTO是否可行呢？  

当使用-flto选项时，编译器会生成中间表示（例如GCC的GIMPLE或LLVM的bitcode），而不是直接的机器码。这些中间文件在最终链接时才会被优化并生成最终的机器码。因此，当编译静态库（.a文件）时，每个源文件生成的目标文件实际上是包含中间表示的文件。  

接下来，用户可能想知道在生成静态库时启用LTO是否有意义。因为静态库只是将多个.o文件打包，并没有链接步骤，所以单独的静态库编译阶段不会进行LTO优化。LTO优化会在使用该静态库链接到可执行文件或其他动态库时发生。
##### 使用方法

(1) 编译生成静态库：
```bash
# 每个源文件必须使用 -flto
gcc -flto -O2 -c file1.c -o file1.o
gcc -flto -O2 -c file2.c -o file2.o

# 打包静态库
ar rcs libmylib.a file1.o file2.o
```

（2）链接静态库，生成可执行文件：
```bash
# 链接时必须启用 -flto 
gcc -flto -O2 main.c -L. -lmylib -o app
```

##### 注意事项
**(1)全链路一致性**
- 静态库的所有目标文件 **必须** 用 `-flto` 编译。
- 最终链接时 **必须** 启用 `-flto`。


如果一个静态库`test.a`，又集成了外部其他的静态库的对象文件，最终想生成集成了所有对象文件的静态库`finnal_test.a`；
那么在集成过程中，如果外部的其他的静态库没有用 `-flto` 编译，那么可能也会没有优化彻底。
比如：**dpdk的编译过程中，没有使用`-flto` 编译，然后，自己的静态库在编译过程中使用了`-flto` 编译，然后自己的静态库中集成了dpdk的静态库的对象文件**。

##### 小结

总结来说，**生成静态库时使用-flto选项是可行的，但实际的优化效果要等到链接时才会体现**。编译静态库时可以开启LTO，但需要注意以下几点：所有目标文件必须使用-flto编译，**最终链接时也必须启用-flto**，并且使用兼容的编译器。这样才能确保LTO优化在链接时正确应用，提升最终生成的二进制文件的性能。

LTO 的使用需要注意以下几点：

- LTO 可能会导致代码的行为发生变化，需要进行充分的测试。
- LTO 可能与某些特定的编译器选项或平台不兼容。

- 安全性要求高的程序，例如金融软件、医疗软件等。
- 代码体积较大的程序，例如大型应用程序、数据库软件等。

### 范例
举例说明如何使用LTO来进行编译优化。
编写了一个包含两个源文件（source1.c 和 source2.c）和一个头文件（source2.h）的程序。由于头文件中非常简单地包含了source2.c中的函数原型， 所以并没有列出。
```c
/* source1.c */
#include <stdio.h> // scanf_s and printf.
#include "source2.h"

int square(int x) { return x*x; }

int main() {
  int n = 5, m;
  scanf("%d", &m);
  printf("The square of %d is %d.\n", n, square(n));
  printf("The square of %d is %d.\n", m, square(m));
  printf("The cube of %d is %d.\n", n, cube(n));
  printf("The sum of %d is %d.\n", n, sum(n));
  printf("The sum of cubes of %d is %d.\n", n, sumOfCubes(n));
  printf("The %dth prime number is %d.\n", n, getPrime(n));
}

/* source2.c */
#include <math.h> // sqrt.
#include <stdbool.h> // bool, true and false.
#include "source2.h"

int cube(int x) { return x*x*x; }

int sum(int x) {
  int result = 0;
  for (int i = 1; i <= x; ++i) result += i;
  return result;
}

int sumOfCubes(int x) {
  int result = 0;
  for (int i = 1; i <= x; ++i) result += cube(i);
  return result;
}

static bool isPrime(int x) {
  for (int i = 2; i <= (int)sqrt(x); ++i) {
    if (x % i == 0) return false;
  }
  return true;
}

int getPrime(int x) {
  int count = 0;
  int candidate = 2;
  while (count != x) {
    if (isPrime(candidate))
      ++count;
  }
  return candidate;
}
```

**编译命令（gcc版本是9.0.1）**
```bash
# Non-LTO:
gcc source1.c source2.c -O2 -o source-nolto

# LTO:
gcc source1.c source2.c -flto -O2 -o source-lto
```

**检查source-nolto的汇编**:
（1）可以发现square被main函数inline了，对于第一次square(n)的调用，由于n在编译时刻可知，所以代码
   被常数25替代，对于square的第二次调用square（m），由于m的值在编译时是未知的，所以编译器不能对   计算估值。

（2）可以发现isPrime被getPrime函数inline了，这是由于candidate有初始值，inline后可以做常量折叠；
   另外一方面，isPrime是static函数，且只有getPrime调用了它，inline之后，可以将这个函数当作dead   code删除，减小代码体积。


**检查source-lto的汇编**
（1）可以看到除了scanf之外的所有函数都被作为了内联函数，因为在GCC LTO的WPA阶段, 这些函数的定义都是
   可见的。并且，由n编译时刻已知，编译器在编译时刻就会完成函数square(n), cube(n)，sum(n)和   sumOfCubes(n)的计算。
（2）LTO获得了30%以上的性能提升。


**结论**
（1）某些优化，当其作用于整个程序级别时，往往比其作用于局部时更加有效，函数内联就是这种类型的优化之一。
（2）事实上，==大多数优化都在全局范围内都更加有效==，这也就是我们编译大型应用程序时，推荐使用LTO的原因和理由。
（3）==FireFox、Chrome、 Mysql等大型应用使用`LTO build`都获得了5%-15%不等的性能提升。==

## 编译器优化技术：`pgo`
### 介绍
PGO，即Profile-Guided Optimization（基于分析的优化），是一种编译器优化技术，通过一个Profile文件，在编译期间，指引（或者说引导）编译器进行指令优化的一个方式，Profile文件则需要通过先运行程序产出，产出后需要利用Profile文件重新编译程序。

### 工作步骤
PGO的工作步骤如下：
**初步编译**：编译器首先对源代码进行一次初步编译，生成一个可执行文件。这个可执行文件会在运行时收集一些性能数据。
**数据收集**：接下来，我们运行这个可执行文件，让它收集性能数据。这通常通过运行一些代表性的任务或者测试用例来完成。
**二次编译**：编译器获取到这些性能数据后，会进行第二次编译，根据收集到的性能数据进行优化。

### PGO是如何提升性能的
PGO优化主要包含几个方向
- 调整分支指令的跳转
- 更为合适地将函数inline

这些优化，==目的其实都是通过调整代码段，使其产生执行时更紧凑的指令，以减少Cache miss的产生==；


#### CPU操作的损耗
CPU操作的损耗，可以参考下图。

如果我们所有指令和数据能一次性放在L1 Cache中，永不Miss，我们执行速度快10倍就有希望了。

#### 调整分支跳转指令如何提升性能
举个例子，我们看下这段代码
```c
int test_func(int x)
{
    if (x > 100) {
        return x / 4;
    }
    return x / 3;
}
```
它产生的汇编（懒鬼必备在线编译器）大概如下图所示：
![](attachments/Pasted%20image%2020250419233121.png)

模拟一下，当我们传入200时，执行cmp，然后发现大于100，就会执行第2行的跳转指令，跳转到第10行;
这个时候，4~9这些指令，都是没有被执行的；
这里就会带来一个**隐形的损耗，就是我们可能会需要重新读主存以把10~13读到L1 Cache中**。
实际上，如果运气足够好的时候，我们在cmp之后的几个指令，可能都会被读到同一个Cache line中（因为数据读进缓存中的大小也是按块来的，通常最小单位就是Cache line 的大小）
如果100次执行里面，99次，x都大于100，那将有可能会把很多无用的代码读到了缓存中。
而在引入PGO之后，我们就可以知道，100次里面，99次，x都大于100，所以我们只需要把两段回编交换一下位置就好，如下图

![](attachments/Pasted%20image%2020250419233355.png)

这里借助一下 `___builtin_expect_` 来模拟这个效果，大概意思是第一个参数的值大概率为第二个参数，其实就是`likely宏`。

回到汇编上，经过调整后，我们执行到3时，仅在小于的情况下才产生跳转，此时我们就减少了再次去访问主存的概率。


#### `调整内联`如何提升性能
继续举例子。假如有这么一段代码：
```c
void test_func_2(int x, int y)
{
    if (x > 0) 
    {
        if (y > 0)
        {
            //假如我在这里悄悄下毒，藏了一个巨大的inline函数
        }
        else 
        {
            //其它简单的操作
        }
        //tag 这里整点很简单的操作
    }
    //其它简单的操作
}
```
当我们命中到`x>0`的判断时，在`y>0`的地方可能会藏了一个内联的函数，它在被展开后可能会占不少地方，这个时候跳转到`tag`的位置时，可能就需要跳过被`inline`的那段代码；
如果在实际情况中，我们大部分都是命中`y<=0`这种条件的话，**实际上内联意义可能不大，不如替换回call来执行，这样`x>0`的判断的代码段就会更紧凑**。



### `pgo`和`lto`
LTO，即Link Time Optimization（链接时优化），也是一种编译器的优化技术。不同于PGO，LTO的优化是在程序的链接阶段进行的。
LTO的工作步骤如下：
**初步编译**：编译器在初步编译阶段，会为每个源文件生成一个包含了中间表示（IR）的对象文件。
**链接优化**：在链接阶段，编译器会读取所有的对象文件，然后在全局范围内进行优化。

#### PGO与LTO的实用例子
为了更好地理解PGO和LTO，让我们看一些实际的例子。
##### PGO的例子
假设你正在编写一个图像处理程序。你可能会发现，在运行时，某些函数被调用的频率比其他函数高得多。
通过使用PGO，编译器可以根据这些运行时信息，优化这些被频繁调用的函数，提高程序的性能。

##### LTO的例子
假设你在编写一个大型软件项目，它包含了很多源文件。在初步编译阶段，编译器只能看到单个源文件的信息，无法获取全局信息。
而通过LTO，编译器可以在链接阶段看到所有源文件的信息，进行更全面的优化。

#### PGO与LTO的优缺点

PGO和LTO都是非常强大的优化技术，但它们也有各自的优缺点。
PGO的优点是它可以实现非常精细的优化，因为它是基于实际的运行情况来进行优化的。但是，PGO需要运行程序来收集性能数据，这会增加编译的时间和复杂性。
LTO的优点是它可以在全局范围内进行优化，这在大型项目中非常有用。但是，LTO会增加链接阶段的时间，并且需要更多的内存。



## 库只显示对外开放的函数符号，其他内部函数符号隐藏
**（1）目标**
自己提供的一个动态库，以及对应的头文件给业务使用，可能是希望通过符号查看命令（比如：`objdump -t xxx.so`）查看动态库的符号时，只能看到对外暴漏的头文件中声明的函数的符号信息。对于其他的动态库的内部函数的符号信息无法查询到。另外一个，自己内部的函数符号进行隐藏，不对外暴漏，也可以防止和外部的库或者外部程序中的函数冲突。

### 业务程序一行不改动的方式调用中间件的库
#### LD_PRELOAD 方式

**符号解析顺序**
当程序调用==动态库==函数时，动态链接器（`ld.so`）会按以下顺序查找符号：
```bash
LD_PRELOAD 指定的库 → 主程序依赖的库 → 标准库（如 glibc）
```

**函数覆盖的本质** 
如果多个库定义了同名函数，动态链接器会选择第一个找到的符号版本。`LD_PRELOAD` 通过强制优先加载用户指定的库，实现函数覆盖。


**使用方法**
```
LD_PRELOAD=/path/to/mylib.so ./myprogram
```

**注意**
LD_PRELOAD 只是新的动态库中的函数，隐藏之前老的动态库（比如：glibc动态库）中的函数。对于，静态函数，或者程序链接的时候使用的静态库
则是无能为力。

```c
int accept(int socket, struct sockaddr *addr, socklen_t *addrlen)
{
	int fd, index, ret;

	if (fd_get(socket, &fd) == fd_rsocket) {
		index = fd_open();
		if (index < 0)
			return index;

		ret = raccept(fd, addr, addrlen);
		if (ret < 0) {
			fd_close(index, &fd);
			return ret;
		}

		fd_store(index, ret, fd_rsocket, fd_ready);
		return index;
	} else if (fd_gets(socket) == fd_fork_listen) {
		index = fd_open();
		if (index < 0)
			return index;

		ret = real.accept(fd, addr, addrlen);
		if (ret < 0) {
			fd_close(index, &fd);
			return ret;
		}

		fd_store(index, ret, fd_normal, fd_fork_passive);
		return index;
	} else {
		return real.accept(fd, addr, addrlen);
	}
}
```
如上所示，对外提供的同名的类socket的接口，如果内部用到了真实的socket接口，那么通过更改名称之后的函数命来调用真实的socket接口。
