# `.so`动态库的加载

当一个 Linux 程序（例如程序 A）启动并加载一个动态库（`.so` 文件）时，动态链接器 (`ld.so`) 会执行以下关键步骤：

- **加载和映射：** 
操作系统会将该 `.so` 文件的内容通过`mmap内存映射`到程序 A 的虚拟地址空间中。这个过程被称为 **内存映射**。

- **内存共享：** 
尽管 `.so` 文件被映射到多个进程（A 和 B）的地址空间，但对于  **代码段和 只读数据段**，操作系统只会加载一份到物理内存中，供所有使用它的进程共享。

- **地址解析：** 
动态链接器会解析程序 A 中对库函数的调用地址，将它们指向共享内存中的库代码。

**关键点：** 
一旦 `.so` 文件被加载到内存中并被程序 A 运行，程序 A 就和磁盘上的原始文件（`*.so`）失去了直接关系。它使用的是内存中的那个映像（Image）。


## 程序启动后加载 `.so` 文件的原理
当一个程序启动并加载一个 `.so` 文件时，操作系统做了两件关键的事情：

### inode (允许替换)
在程序开始执行后，加载器打开了 `.so` 文件。操作系统会通过文件的 **inode** (索引节点) 来跟踪文件，而不是文件名本身。

- **可以替换/删除：** 你可以删除或重命名原来的 `.so` 文件，然后创建一个新的同名文件（即替换）。因为操作系统仍然通过旧的 inode 引用着那个文件内容，所以程序会继续使用旧的、已被删除或重命名的文件内容。
    - **优点：** 这种行为允许在不停机的情况下部署新版本程序。你替换了 `.so` 文件，但正在运行的旧程序不受影响，只有下次启动的新程序才会加载新 `.so`。
        
- **不能更改/截断：** **正在使用的文件（旧的 `.so` 文件）不能被修改（如用 `echo` 写入/cp 同名覆盖）或被截断（如用 `truncate` 改变大小）。** 如果尝试这样做，你会收到 "Text file busy"（文本文件忙）或 "Permission denied" 等错误，因为操作系统正在通过内存映射（Memory Mapping）保护它。

### `mmap()`内存映射

操作系统使用 `mmap()` 调用将 `.so` 文件中的代码和数据段映射到进程的虚拟地址空间。
**代码段（.text）是只读的。** 操作系统将其标记为只读，以防止程序意外修改自身代码。这是阻止你修改文件的主要原因。操作系统发现进程正在使用这个文件（特别是它的只读代码段），为了保证运行中的程序的完整性和安全性，它会锁定这个文件上的写入操作。

#### `/proc/PID/maps` 字段解析

一个典型的 `/proc/PID/maps` 文件条目示例如下：
```bash
7fe3a3a66000-7fe3a3a79000 r--p 00000000 08:02 405890                     /usr/lib64/libkucl.so
7fe3a3a79000-7fe3a3ccb000 r-xp 00013000 08:02 405890                     /usr/lib64/libkucl.so
7fe3a3ccb000-7fe3a3d5c000 r--p 00265000 08:02 405890                     /usr/lib64/libkucl.so
7fe3a3d5c000-7fe3a3d5d000 ---p 002f6000 08:02 405890                     /usr/lib64/libkucl.so
7fe3a3d5d000-7fe3a3d63000 r--p 002f6000 08:02 405890                     /usr/lib64/libkucl.so
7fe3a3d63000-7fe3a3de0000 rw-p 002fc000 08:02 405890                     /usr/lib64/libkucl.so
```

|**字段序号**|**字段名称**|**描述**|
|---|---|---|
|**1**|**Address Range**|**内存地址范围**，格式为 `起始地址-结束地址`。这是该映射区域在进程虚拟地址空间中的十六进制范围。|
|**2**|**Permissions**|**内存访问权限**。由四个字符组成。|
|**3**|**Offset**|**文件偏移量**。如果该区域映射自文件，这是文件内对应的偏移量（十六进制）。对于匿名映射（如堆、栈、匿名 mmap），该值为 `00000000`。|
|**4**|**Device**|**设备号**。映射来自哪个设备，格式为 `主设备号:次设备号`（十六进制）。对于匿名映射，该值为 `00:00`。|
|**5**|**Inode**|**文件的 inode 号**。如果该区域映射自文件，这是该文件的 inode 编号。对于匿名映射，该值为 `0`。|
|**6**|**Pathname**|**映射路径名**。如果该区域映射自文件，这是文件的完整路径。对于匿名区域，可能显示特殊标记。|


##### Permissions (权限)字段

权限字段由四个字符组成，定义了进程对该内存区域的访问权限。

|**字符**|**含义**|**说明**|
|---|---|---|
|**r**|**read**|可读。进程可以从该区域读取数据。|
|**w**|**write**|可写。进程可以向该区域写入数据。|
|**x**|**execute**|可执行。进程可以将该区域的代码执行。|
|**p**|**private**|**私有映射**（Copy-on-Write）。对该区域的修改只对当前进程可见。|
|**s**|**shared**|**共享映射**。对该区域的修改对所有映射该文件的进程可见。|

**常见组合：**
- **`r-xp`**: **代码段（.text）**。可读、可执行、不可写，私有（来自文件或库）。
- **`rw-p`**: **数据段（.data）**、**堆（[heap]）**、**栈（[stack]）**。可读、可写、不可执行，私有。
- **`r--p`**: **只读数据段（.rodata）**。可读、不可写、不可执行，私有。

##### Pathname (映射路径名)字段

该字段指示了内存区域的来源，是理解内存布局的关键。

|**路径名**|**含义**|
|---|---|
|**/path/to/executable**|**程序的可执行文件**本身（代码段、只读数据等）。|
|**/path/to/library.so**|**共享库**文件（如 `/lib64/libc.so.6`）。|
|**`[heap]`**|进程的**堆**（Heap）区域，用于动态内存分配（`malloc`）。|
|**`[stack]`**|进程的**主线程栈**（Stack）区域，用于局部变量和函数调用。|
|**`[vdso]`**|**Virtual Dynamically linked Shared Object**。内核提供的一种机制，包含一些系统调用（如 `gettimeofday`）的快速实现，避免陷入内核态。|
|**`[vvar]`**|**Virtual Kernel Variables**。内核用于暴露一些只读变量的区域。|
|**`[anon]`** 或 **匿名映射**|通常是进程通过 `mmap()` 调用创建的**匿名私有内存**，不对应任何文件。|




# 动态库的升级
## 场景
linux 中，某个程序A和程序B依赖于某个.so的动态库；此时将程序B停了，A依然在运行。然后将.so库升级，使得B使用新的so库进行启动。那么此时A程序是否受到影响？

## 库文件的升级与替换

当您在程序 A 仍在运行时替换磁盘上的 `.so` 文件时，会发生什么：

- **程序 A (旧版本)：**
    - 它正在使用的内存映像（包括代码和数据）**保持不变**。
    - 操作系统允许您删除或替换磁盘上的文件，即使该文件仍被打开。
    - 因此，程序 A 会继续 **安全、稳定** 地使用内存中的旧版库代码。


- **程序 B (新版本)：**
    - 程序 B 停机后，它占用的旧版库的内存引用被释放（如果它是最后一个使用者，操作系统可能会释放部分物理内存）。
    - 当您重新启动程序 B 时，动态链接器会再次查找磁盘上的 `.so` 文件。此时，它找到的是**新替换的那个文件**，并将其加载和映射到程序 B 的地址空间中。
    - 因此，程序 B 将使用新版库代码运行。



### 注意事项
升级`so`文件，可以用新的`so`文件直接替换旧的`so`文件，但是不可以更改。即：`可以替换so，不能更改so`；
即：不可以使用cp来进行升级，可以通过mv 或者 rm 来替换。

#### `cp` 替换同名库文件
`cp new_xxx.so /lib64/xxx.so`替换出现`bus error 段错误`问题。

使用 `cp new old` 替换同名文件时，`old` 文件的 inode **不变**，但其内容被替换。

|**步骤**|**操作**|**结果**|
|---|---|---|
|**步骤 1**|`cp new old`|1. `cp` 命令会**打开** `old` 文件（inode不变）。 2. 它会**清空** `old` 文件的所有内容（截断）。 3. 它将 `new` 文件的内容**写入**到 `old` 文件中。|
|**inode 变化**|`old` 文件的 inode **不变**。|文件的权限、所有者、创建时间等元数据保持不变（但修改时间会更新）。|
|**旧文件**|旧文件的内容**被覆盖**，而不是旧文件被删除。|磁盘上的数据块被 `new` 文件的内容所取代。|
|**原子性**|**非原子操作**。|如果复制过程中断电或发生错误，`old` 文件可能会损坏或只包含部分内容。|


#### `mv` 替换同名库文件

使用 `mv new old` 替换同名文件时，旧的 `old` 文件被删除，文件的 inode **会变**，换成新的inode。


### 已启动程序什么时候受到影响

已启动程序（程序 A） 只有在以下情况下才会受到新 `.so` 文件的影响：

**（1）程序 A 重启：** 
如果您重启程序 A，它会像程序 B 一样，重新加载磁盘上的 `.so` 文件，从而使用新版本。

**（2）动态链接 (Dynamic Linking) / 懒加载：** 
如果程序 A 使用了 `dlopen()` 来动态加载这个库，并且是在升级后才执行 `dlopen()`，那么它也会加载新版本。
但如果是在升级前就已经 `dlopen()` 并且没有 `dlclose()`，则不会受到影响。
如果是在升级后，`.so` 被程序A以极特殊方式（比如：`dlclose`）卸载并重新 `dlopen`，就会用新版本，但普通程序一般不会这么做。


# 动态库的热更新
## 背景：静态依赖的库(ldd 显示的那些)的升级

- **替换：** 可以替换 `.so` 文件
> 注：不可以通过cp来替换，cp是文件的inode不变，替换的内容。
    
- **效果：** 正在运行的程序 不会 使用新的 `.so`。它会继续使用加载到内存中的旧代码。只有当程序下次启动时，才会加载新的 `.so` 文件。

- **原因：** 这些库在程序启动时就已经被通过`mmap`内存映射加载器固定映射到内存了。



## 热更新
在程序运行过程中替换 `.so` 文件并让程序使用新版本，需要依赖 **动态加载（Dynamic Loading）** 机制，即使用 `dlopen()` / `dlsym()` / `dlclose()` 函数族。

### 动态加载的库 (dlopen 实现)

- **程序运行**：程序通过 `dlopen()` 加载 `libplugin.so`，并开始调用其中的函数。
    
- **卸载旧版本**：程序调用 `dlclose()` 显式地卸载 `libplugin.so`。此时，如果没有任何其他程序或进程再使用这个库，操作系统会解除文件的内存映射。
    
- **替换文件**：在 `dlclose()` 之后，你可以安全地将 `libplugin.so` 替换为新版本。
    
- **加载新版本**：程序再次调用 `dlopen()` 加载新的 `libplugin.so`。此时，程序将开始执行新版本的代码。


**注意：** 实现这种热更新需要精心设计，确保新旧版本之间的接口（ABI）兼容，并且在 `dlclose` 之前处理好所有旧版本库中的资源释放。
