**整体流程**：
Agent利用`ebpf uprobe`技术在libnccl库中设置钩子，当业务进程触及这些钩子函数时，它会被激活并执行特定的操作。借此方法，Agent可以实时捕获libnccl库中的QP、端口等关键信息。
当Agent成功获取这些数据后，它将通过Raw socket构造并发送一个INT探测包（dip=实际业务流的dip）。一旦接收端的Agent检测到这个探测包，XDP程序会立即响应，将探测包封装成Vxlan报文，选择正确的网卡（XDP Redirect 到 TCP平面的网卡）转发至监控机。监控机器会解读这些报文的内容并为用户呈现相关数据。

# Uprobe：发送端探测用户态函数

uprobe是eBPF提供的一个强大功能，专为用户空间应用程序设计。它允许开发者为用户空间中的应用程序设置**特定的函数或指令断点**。
一旦这些断点被触发，关联的eBPF程序将立即执行，从而允许用户收集有关程序运行状态的实时信息。
相较于传统的追踪和调试方法，uprobe提供了一种低开销、高效率的解决方案。它不仅对于深入了解应用程序的性能瓶颈或行为异常至关重要，还常被用于安全分析，帮助检测可能的恶意行为或异常函数调用。与uprobe在用户空间的操作相对应的是kprobe，专门用于内核空间的函数和指令追踪。这两者的结合为系统管理员和开发者提供了一个全面的、端到端的观测手段。

![](attachments/image%20(48).png)

Uprobe 注入函数的原理：当我们将 uprobe 定位到目标函数，如 user_fun 时，系统会在该函数的入口处植入一个特殊的 "int3" 中断指令，每当这个函数被调用并执行到入口点时，该 "int3" 指令会立即触发一个中断。这个中断并不是普通的执行流程。当它被触发，系统的中断处理机制会查找到与此 uprobe 关联的 eBPF 程序，并立即开始执行，eBPF 程序就能够在目标函数开始执行前捕获其上下文和数据。完成捕获后，eBPF 程序可以选择将相关数据存储在map 中。这个 map 是内核与用户空间之间进行数据交互的关键。通过这样的方式，外部agent就可以随时读取 map 中的内容，进而获得有关函数调用的详细追踪信息。

# XDP：接收端识别INT流量Vxlan封装给监控机

![](attachments/image%20(47).png)

当sink节点（接收端）接收到INT报文时，它首先会验证IP报文中的协议字段。如果这个字段的值是253，这意味着报文是一个INT报文。确认后，sink节点会采取进一步的操作：它将INT报文封装到一个Vxlan数据包中，作为其负载。完成封装后，sink节点将这个Vxlan数据包转发给INT分析系统，以便进行后续的数据分析和处理。

## Native XDP程序：INT流量识别

![](attachments/image%20(46)%201.png)

**（1）eBPF程序的应用场景分类**：
根据其功能和应用场景，我们可以将eBPF应用程序大致划分为以下三类：
1》跟踪与监控：这类eBPF程序主要用于从内核及应用程序中抽取运行信息，帮助我们深入了解系统的实时运行状况。
2》网络处理：这类程序主要针对网络数据包，进行深度的过滤和处理，使我们能够详细了解并精准控制网络数据的传输流程。
3》安全与策略扩展：这部分的eBPF程序主要聚焦于系统的安全性，通过BPF来增强和细化安全策略和控制。


**(1.1)网络处理类的ebpf 分类**：
网络类的 eBPF 程序在 Linux 网络堆栈的多个层面都有应用。以下是一些常见的网络类 eBPF 程序类型和它们的应用场景：
1》XDP (eXpress Data Path)：XDP 允许 eBPF 程序在网络驱动层面处理数据包，这是数据包进入内核的最早阶段。由于其高效性，XDP 常用于高速数据包过滤、负载均衡和DDoS防御。
2》Traffic Control (tc) BPF：tc BPF 允许在更高层的网络栈中处理数据包，常用于复杂的数据包过滤、路由。
3》Socket-level BPF：这种 eBPF 程序可以与特定的套接字关联，允许对套接字级别的数据进行过滤和处理。常用于套接字级别的策略执行、安全和监控。
4》BPF Cgroup hooks：这种 eBPF 程序允许在cgroup层面进行数据包处理，从而为特定的进程组提供网络策略。常用于容器和进程级别的网络策略和监控。

**（1.2）XDP的三种模式**：

XDP定义为BPF_PROG_TYPE_XDP，它在网卡驱动程序接收到数据包时触发。由于XDP程序直接在数据包接收时介入，避免了复杂的内核网络协议栈处理，因此它能够提供高效的网络处理能力。
XDP有三种运行模式：
1》通用模式（Generic XDP）：此模式不依赖特定的网卡或其驱动程序。在这里，XDP程序在内核中运行，就像传统的网络协议栈那样。由于其通用性，性能可能不是最佳，但它非常适合测试和原型开发。
2》原生模式 (Native XDP)：这要求网卡的驱动程序提供支持。在原生模式下，XDP程序在网卡驱动的早期处理路径中执行，从而实现更高的性能。
3》卸载模式( Offload XDP)：在此模式下，网卡的固件必须支持XDP卸载功能。这意味着XDP程序直接在网卡上运行，完全绕过主机CPU，从而实现最高的性能。

处理完数据包后，XDP程序必须根据其执行结果确定数据包的下一步。这些决策是基于XDP程序的五种可能的结果码来进行的：

|  XDP动作 | 含义  |
|---|---|
|XDP_DROP|丢弃|
|XDP_PASS|不做处理，传递到内核协议栈|
|XDP_TX|转发数据包到同一网卡|
|XDP_REDIRECT|转发数据包到不同网卡|
|XDP_ABORTED|XDP程序运行错误，数据包丢弃|
