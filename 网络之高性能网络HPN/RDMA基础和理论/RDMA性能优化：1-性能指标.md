# 性能指标
## 时延
延迟是用户感受到的时间（比如，通过前端APP）。
### 时延分类
网络时延，简单来说，就是数据在网络上传输所需的时间。它可以细分为静态时延和动态时延。

#### 静态时延
静态时延，像是网络硬件的“天生”属性，包括互联（物理线路的时延）、转发和交换等过程，它相对稳定，主要由物理布局和设备性能决定。

**静态时延拆分**：
（1）物理线路的时延：一般来说1m的传输大概耗时是5ns。
（2）交换机转发时延（即中间节点每一跳转发的时延）：不考虑在交换机队列中缓存的时间，每经过一个交换机设备的时延是1us。
（3）端侧网卡转发时延：

#### 动态时延
动态时延则像是个“情绪化”的孩子，会随着网络负载、带宽利用率等因素波动，随时可能变化。
例如，通过UEC优化以太网，主要就是减少了这种“情绪化”的时延。

**动态时延 举例**：
（1）队列排队时延
（2）丢包重传时延
（3）程序 cache miss 或者加锁的时延。
（4）内核转发的时延。

### 端到端通信的时延拆分
#### 端侧时延
端侧的时延，分为：
（1）端侧程序的时延「动态时延」：比如程序 cache miss 或者加锁的时延
（2）端侧内核转发的时延「动态时延」：数据(报文)在内核中转发的时延。
（3）端侧网卡的排队的时延「动态时延」。
（4）端侧网卡转发的时延「静态时延」。

#### 物理线路的时延
通过数据线路进行转发，也有一定的时延「静态时延」；

==100km光纤的RTT是1ms，100m的RTT就是1us，1m的传输大概耗时是5ns==
交换机的转发时延约为0.8us（单向）。

### 注意事项
用户使用RDMA通讯库中间件进行测试时 ，应该分为：
（1）网络层面的时延：即RDMA通讯库（通讯库软件，物理网络「比如：网线，中间的交换机」、 终端的RNIC网卡）
（2）业务逻辑层面的时延：

注：比如要区分这2个时延，否则很多业务使用RDMA通讯库中间件的时候，通过业务自己的测试程序的时候，发现时延很高。
==对于这种常见，需要RDMA通讯库中间件有自己的Trace功能，将通信库自身的关键函数、关键字段打印出来，同时打印出对应的时刻==。
这样可以在业务测试程序的时延较高时排除通讯库中间件自身的影响。

#### 网络层面时延的测试
测试网路层面的时延，那么就需要抛开业务的时延带来的干扰。

RDMA网络层面影响时延的因素：
（1）由于QP的数量过多会严重影响性能, 导致时延高；
（2）由于带宽的限制，也会导致发送的排队，这个也会影响性能。
比如：25G的Mellanox设备，没有进行网口bond的情况下，写4K的数据。
为了不排队，那么1us最多可以写多少的数据呢？
25Gbps/8 = 3G Bps。那么1us 就是 3K B的数据。那么如果写4K的数据，大概就是1.3us。
如果RDMA的client到Server的RTT是8us，那么8us/1.3us = 6；
也就意味着单机一次最多burst发送 6个4K的数据，才不会排队；更多的burst，就会导致排队。

测试：
```bash
测试一：
（1）背景流：建立占用多个QP，同时少占用带宽。
背景程序创建N个QP，每个连接发送少量的字节数。

（2）业务流：
只有一个连接，测试这样连接的时延是否收到背景流的QP的数量的影响。

注：RNIC是否也有类似于CPU那样，有PPS的限制，比如CPU那样有PPS的限制。比如：100G的RNIC网卡，每次发100B的数据，能否达到100G的限速；如果是1B的数据呢，是否可以达到100G的限速。

测试二：
提前建立500个QP，每个RPC请求，随机的选择1个QP，从微观上好像只会使用一个QP，宏观上每个QP都会被使用。
```

#### 范例

![](attachments/test11.png)

如上所示，是BS端的trace日志。
上面是client设置io-depth为1时，bs到某个cs的trace；下面是io-depth为6时，bs到这个cs的trace；
从trace的日志中，可以看到，io-depth为1时，单个rpc的时延为9us左右；io-depth为6时，单个rpc的时延为22us左右；主要是由于io-depth为多个时，在KRPC软件层面中可能存在等待「某个RPC接收响应之前穿插了其他的RPC请求的发送」。


由上，当client设置io-depth为N（N>1）时，那么对于某个RPC请求而言，就会在KRPC软件层存在由于发送其他RPC的请求带来的等待。这个等待时间也被计算到了RPC时延当中。
如果为了考量RDMA中间件KUCL的性能「如：时延、IOPS」以及QP数量增大带来的影响，那么就应该抛开KRPC软件层面的等待时延带来的影响，也就是意味着不可以设置IO-Depth大于1进行测试，这样测试的结果才可以近似的和RDMA测试工具Perftest进行粗略的对比。

**（1）read/write测试**
```bash
(1) Server端：
背景流：
ib_write_bw -d mlx5_0 -x 3 -q 1000 -s 2050 -F --run_infinitely -p 18519 --report_gbits
测时延：
ib_write_lat -x 3 -d mlx5_0 --report_gbits -s 4096 -n 1000 -p 18516 
ib_write_lat -x 3 -d mlx5_0 --report_gbits -a -p 18516 

(2) client端： 
背景流：
ib_write_bw -d mlx5_0 -x 3 -q 1000 -s 2050 -F 27.105.180.3 -p 18519 --report_gbits --run_infinitely 
测时延：
ib_write_lat -x 3 -d mlx5_0 --report_gbits -s 4096 -n 1000 27.105.180.3 -p 18516
ib_write_lat -x 3 -d mlx5_0 --report_gbits -a 27.105.180.3 -p 18516

参数说明：
    -d：指定IB设备
  -x: 指定gid index；
  -q: 指定qp数量，只有测试带宽时可用
  -s: 指定io size;
  --run_infinitely: 程序一直运行
  -p: server端监听端口或者client端指定server端的端口
  -n: 数据交换迭代测试，也是 post_send 的次数；注意不是QP的深度；
  -t, --tx-depth=<dep> : QP 发送队列的深度，默认是128；
  -r, --rx-depth=：QP的接收队列的深度，默认512；
  -a: 测试各个io-size(从4,8,16,32,64,..., 一直到, 默认每个io-size的测试次数为1000次)的时延;
  -l, --post_list=<list size>: 一次post_send 最多是多少个WR；默认一个WR下只有一个sge；
      --recv_post_list=<list size> : 一次post_recv 最多含有多少个recv_wr，默认每个wr下只有一个sge;
  -b: --bidirectional  Measure bidirectional bandwidth (default unidirectional); 双向测试，即 接收和响应都有数据。
  -D, --duration: 运行时长，以秒为单位。和 -n 类似；
  
server端设置`-s` 应该是为了设置post recv wr的buf的大小。
```

8个线程时，**如上所示，`io-depth`为8时，已经将带宽打满，此时qp数量提升，时延基本不变。可以将`io-depth`「反应了软件层面，每个线程`post wqe`发送数据的能力」继续提升，则此时带宽还是打满，时延会继续大幅增大**。
如下所示：设置`8`个线程，每个线程`200`个QP，设置每个线程的`io-depth`为`50`的时候，此时带宽打满，时延达到了`150us`。

#### 流程分析
整体流程：
    软件执行RDMA数据面操作(Post send发送WR) ------> RNIC网卡DMA通过PCIe取数据WQE执行的数据----->网卡发送数据


##### QP轮询机制
每QP的WQE会在TX方向的MQ（Message Queue）里排队等待处理，排队的策略是FIFO（First In First Out）
轮到后每WQE会最多发送8KB的数据，之后更新QPC，然后将当前WQE放到MQ的最后继续排队
根据当前测试结果看，在TX方向非满情况下，QP间的轮询是非常快的，由于QP轮询带来的每QP转发延时十分有限

##### 造成网卡TX满带宽时延时增大的原因：

网卡从应用层产生WQE，到网卡处理WQE，再到进入转发队列进行报文封装，最后发送出去，整个过程是个pipeline，为保证尽可能低的转发延时，从`PCIe->Network`这个方向上每个stage间没有`flow control`;
由于PCIe Gen4.0 x16的物理带宽为230Gbps，网络物理带宽为200Gbps，所以存在从`PCIe->Network`这个方向上的“大打小”。
当软件post wqe发送数据的速度超过了200Gbps时，网卡硬件TX按照200Gbps持续发送，由于无法进一步提高发送速度，首先受冲击的是Network MAC模块，当达到一个阈值后，会从MAC模块逐级向PCIe端发送BP（Back Presure）信号。出现BP信号后，从PCIe侧过来的待发送数据就会在网卡上产生堆积，逐渐占满网卡的`onchip buffer`。
硬件处理WQE时需要网卡DMA模块从`Host Memory`拉取数据到`onchip buffer`，请求onchip buffer空间时就会连续超时/重试反复进行，此过程会产生大量延时。

#### 总结


QP数量提升和时延之间的关系：其实主要还是看软件Post send发送WR对应的数据的速度 和 网卡硬件发送数据的速度的对比。

1> 带宽未满时：意味着此时软件Post send发送数据的速度「通过io-depth、线程个数、io-size等控制程序发送数据的速度、或 多个程序同时执行」小于网卡发送数据的速度。

随着QP数量「如每个线程的连接从100->1600」的提升，时延略微提升「平均时延大概从11us->13us，实际提升大约是1.7us」
随着QP数量「如每个线程的连接从100->400」的提升，时延略微提升「平均时延大概从11us->12us，实际提升大约是0.9us」

注：qp数量提升，时延略微有所提升，主要是cache-miss导致，即软件导致（虽然cache-miss是硬件事件，此中将其归结于软件）。并不是说，RNIC网卡导致的。

2> 带宽（接近）满时：意味着此时软件Post send发送数据的速度大于网卡发送数据的速度。
此时无论是背景流，还是测试流，都存在软件`post send` 发送数据的速度过快，网卡硬件发包速度不够，而导致的重试/排队问题，进而带来了高时延。

### 时延的优化
**减少时延**：  
（1）每个fd内：
发送一个请求，需要接收响应。在这个请求和响应中间，这个连接不可以发送其他的请求。 

（2）多个fd间：
某个fd发送一个请求，然后其他的fd可写时，也发送请求，但是其他可发送请求的fd的数量需要限定。如果其他的可发送请求的fd太多，且不限定发送；那么也会导致前面的fd发送的请求的响应可能都到达了，这边还在发送其他fd的请求，导致时延偏大。  
解决办法：可以加一个线程粒度的io-depth，限定一个线程内，一次性最多可以多少个RPC请求。比如io-depth为N，将每个RPC随机的分给某个fd，每发送一个RPC，则线程的io深度--；线程的io深度非0时，才允许选择某个fd进行发送，否则不允许发送。每收到一个RPC响应，则线程的io深度++；

从==生产者-->消费者的角度==来看这个问题。==一般存在瓶颈，就是生产者、消费者，或者生产者和消费者之间的缓冲区哪里存在瓶颈==。

```bash
（1）端到端的请求和响应角度：

1> 请求：client----->server
client 是生产者，server 是消费者

2> 响应：server----->client
server 是生产者，client 是消费者


(2) 从单个节点的角度来说：（此中拿client举例）
对于QP的SQ: 生产者是软件(基于CPU的应用)，消费者是硬件, 缓冲区是队列深度；
对于QP的RQ: 生产者是软件(基于CPU的应用)，消费者是硬件, 缓冲区是队列深度；
对于CQ: 生产者是硬件，消费者是软件(基于CPU的应用), 缓冲区是队列深度；

(3) 从应用程序发送数据到发送出去的流程来说：
client的应用程序调用writev接口来发送数据---->通讯库基于writev的参数iov信息，封装内部的skb信息，进而填充wr的信息，然后调用post_send 来下发send_wr----> 敲DB(doorbell)----> DMA通过PCie 从指定的内存地址中取数据到硬件缓冲区------>网卡从硬件中取数据发出去。

1> 软件post_send, DMA取数据
生产者是软件，消费者是DMA(通过PCIe的方式)

2> DMA取数据，网卡发送
生产者是网卡中的DMA，消费者是网卡，缓冲区是硬件缓冲区。
如果网卡带宽打满，说明DMA放数据的速率 > 网卡发送数据的速率。此时硬件缓冲区会被打满，后续DMA取数据，放入到硬件缓冲区就会失败，就会不断的重试，进而降低DMA成功放入数据的速率。这个时候就会导致时延变大。

3> 综合
一般而言，PICe的带宽大于网卡的带宽。
<A> 如果说：软件Post_send post 对应数据的带宽 ≃（约相等） DMA通过Pcie取数据的带宽 > 网卡的硬件带宽；
这个时候，网卡硬件带宽就会打满，这个时候，在网卡硬件就存在排队。

<B> 如果说：软件Post_send post 对应数据的带宽 > DMA通过Pcie取数据的带宽;
这个时候，SQ就会被打满，此时可能需要进行限速。通过软件计数器记录每个QP的SQ的可用深度，同时在软件中存在一个缓存未发送的数据。
```

## bond导致的性能瓶颈
### QP是Per物理口分配的
一个QP只能分配到一个物理网卡上，对于bond模式，如果只用一个QP，最多只能打满单个物理网卡；无法打满bond口下的各个物理口的带宽。

### SRQ导致的性能问题
#### 问题
bond模式下，使用rdma，然后使用了srq；一个线程中只有一个srq，该线程下创建了多个conn(即多个qp)，发现存在性能问题。比如100G网卡，发送4K的数据，只能打60G？帮我分析下性能瓶颈点。

#### 分析

**SRQ 的锁竞争与串行化瓶颈 (最核心原因)**

SRQ 的初衷是让多个 QP 共享同一个接收缓冲池。但在硬件和驱动底层，SRQ 的资源分配是存在锁或串行化机制的。

- **硬件竞争**：当多个 QP（连接）同时从**同一个 SRQ** 中提取 WQE（工作请求描述符）时，网卡硬件内部的调度器必须对 SRQ 的 Head 指针进行同步。
    
- **并发瓶颈**：100G 网卡内部有多个硬件处理引擎。如果使用多个 SRQ，流量可以分发到不同的引擎；但如果你强制**所有 QP 共享一个 SRQ**，所有接收路径最终都会在 SRQ 这一层级“汇聚”，形成一个串行化断点，限制了并发处理能力。

#### 其他
**背景**
bond模式下，使用rdma，然后使用了srq，发现使用SRQ，比不使用SRQ，从时延上看，使用SRQ性能还好一些呢。这也是为什么当初使用SRQ，但是使用了之后，发现了上面说的问题，带宽打不上去。


**分析**
RDMA 架构中内存管理与并发处理之间的权衡（Trade-off）。

在不使用 SRQ（即使用每个 QP 独立的 RQ）时，时延通常受以下因素影响：
```bash
Cache Locality (缓存亲和性)： 
如果你有大量 QP，每个 QP 都有自己的接收队列，这些队列分布在内存的不同位置。当网卡频繁切换 QP 处理接收时，CPU 和网卡的 Cache 需要不断加载不同的队列元数据。
    
WQE Fetching (获取描述符)：硬件在处理接收前，必须从主存抓取 WQE。
独立 RQ：网卡需要维护成百上千个队列的状态指针，容易导致网卡片上缓存（On-chip Cache）溢出。
SRQ：所有的 QP 都去同一个“池子”里拿 WQE。网卡只需要维护一个 SRQ 的上下文。
对于硬件来说，这大大提高了元数据的命中率，减少了从主存获取描述符的次数，从而降低了单次请求的起始时延。

```

当你开始追求极限带宽（High Throughput/PPS）时，性能瓶颈从“元数据查找”转移到了**资源竞争和串行化处理**。
```bash
### A. 锁竞争 (Serialization Hook)
在底层硬件逻辑中，SRQ 必须保证 WQE 分配的原子性。
- 当 100G 的流量涌入，多个 QP 同时请求从 SRQ 中 Pop 一个 WQE 时，SRQ 的头部指针（Head Pointer）成为了全系统的热点（Hotspot）。
- 由于只有一个 SRQ，硬件在处理 WQE 分配时必须进行硬件级别的加锁或排队。这种“多对一”的竞争在高 PPS 下会产生明显的排队延迟，限制了单位时间内能处理的包数量。


### B. 单线程轮询的极限
你提到“一个线程只有一个 SRQ”，这意味着你可能也只有一个 Completion Queue (CQ)。
- PPS 墙： 4K 数据包跑 100G 约需 3M+ PPS。单线程在处理 `ibv_poll_cq` 时，除了取出 CQE，还要进行后续的业务逻辑（比如内存重用、协议解析）。
- 无法并行： 如果你不使用 SRQ，你可以创建多个 CQ 并绑定到不同的 CPU 核心上（RSS/Multi-Queue 思想）。但由于你共用了 SRQ，为了维护逻辑一致性，你很难在不引入复杂同步机制的情况下实现真正的多线程并行化。
```


|**维度**|**独立 RQ (Per-QP)**|**共享 SRQ**|
|---|---|---|
|**内存开销**|高 (每个 QP 都要预留大量 WQE)|**低** (按需分配，适合海量连接)|
|**元数据 Cache 命中率**|较低 (连接数多时容易抖动)|**极高** (网卡只盯着一个队列看)|
|**小并发时延**|略高|**更优**|
|**高并发吞吐 (Bandwidth)**|**更强** (易于多核并行，无竞争)|较弱 (受限于 SRQ 锁和单线程)|



#### 建议
不要全局只用一个 SRQ。建议根据 CPU 核心数或网卡硬件通道数，创建 **多个 SRQ**。
例如：16 个 QP 共享 SRQ_1，另外 16 个 QP 共享 SRQ_2。这样可以有效降低硬件层面对共享队列的竞争。


如果你想突破 60G 的瓶颈，建议尝试以下架构演进：
1. **Multi-SRQ 方案：** 不要只用一个 SRQ。根据 CPU 核心数，创建 4-8 个 SRQ，将几百个 QP 均匀分布到这几个 SRQ 上。这样既保留了 SRQ 节省内存和元数据高效的优点，又分散了锁竞争。
2. **开启 RSS (Receive Side Scaling) 思想：** * 将连接分散到不同的 CQ。
    - 每个 CQ 绑定独立的 CPU 核心进行 Polling。

3. **检查 Bond 的 Hash 算法：** 确保流量不是全部堆积在 Bond 的某一个物理成员端口上。对于 RDMA，通常建议使用 L3+L4 的 Hash。
