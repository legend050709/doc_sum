# MTU大小和性能的关系

## DPDK中调整MTU和性能的关系
### 背景
比如：发送4K的数据，默认网卡的MTU是1500，通过三次握手协商出来的MSS也是1460；
那么将MTU从1500，更改为4200，进行性能对比。

### 分析
**测试结果**：
发现实际将将MTU从1500，更改为4200，基于用户态协议栈(DPDK)的库的性能并没有太多提升，但是业务调用readv时，返回给业务的iov的个数的确减少了。

**分析**：
```bash
(1) 性能提升少：
比如：正常发送4K(4096)B的数据，如果使用MTU 1500， 那么需要三个包。如果是使用MTU 4200， 则只需要一个包即可。
现在的问题是，如果是应用发送4K的数据，使用MTU 1500，用户态协议栈使用3个PKT来承载；用户态实现的协议栈，大概率是这三个包是一次性批量发送出去的，而不是发一个，收到ACK，再发送下一个。
这和MTU 4200时，只发送一个包，其实在中间网络消耗的时间差不多。

差别就是：用户态协议栈收发的时候用三个包承载，这部分消耗的性能有限。

因此，MTU提升到4200，整体的性能提升有限。

(2) IOV个数减少：
用户态协议栈每收到一个数据包（mbuf），就对应一个IOV，无论这个数据包的大小。而收到的数据包的大小，和两端的MTU有关系。
因为用户态协议栈是零拷贝(ZC: zero-copy)的，收到的多个mbuf的地址是不连续的，无法将多个mbuf并为一个iov。
```

### 分析


**MTU 变大，本质只减少一件事：`packet 数量 (pps)`；如果 pps 是瓶颈，MTU调大应该看到提升**。

在传统内核栈中，增大 MTU 的核心收益是减少协议栈遍历次数。
- **内核栈 (MTU 1500, 4KB 数据)**: 需要 1 次或以上的中断（如果是NAPI，可能也是一次中断）、3 次 SKB 分配、3 次协议头解析。
- **内核栈 (MTU 4200, 4KB 数据)**: 只需 1 次中断、1 次 SKB... 。

例如发送 4KB的 数据：MTU=1500B，则需要3个packet；MTU=4200B，则需要1个packet；
很多人直觉认为：`3 packets` 带来了 `latency ×3`，其实完全不是。现代 NIC pipeline 是：
```bash
WQE
↓
segmentation
↓
packet pipeline
↓
MAC
```
3个packet的发送是流水线发送。
```bash
packet1 start
packet2 start
packet3 start
```

串行化时延 (Serialization Delay)：
```bash
- 在 100Gbps 网卡链路上：
    - 1500 Byte 包： ≈120ns, 1500 * 8 / 100G  ≈ 120ns
    - 4200 Byte 包： ≈336ns, 4200 * 8 / 100G  ≈ 336ns

典型 RDMA RTT 是 3–6 µs，所以影响很小，实际测量几乎看不出来。
```

kernel-bypass 的系统：
```bash
application
↓
WQE / mbuf
↓
NIC pipeline
```
**CPU处理的是 message, 而不是 packet**。至于基于DPDK的用户态协议栈，将Message按照MTU划分为多个packet的开销，基本可以忽略不计（因为不涉及到拷贝）。
```bash
- 场景：你要发送 4KB 数据。
MTU 1500：你的程序构造 1 个 大的工作请求 (WQE for RDMA)，告诉网卡：“这里有 4KB 数据，发出去”。网卡硬件引擎会在内部自动将其切分为 3 个符合 MTU 限制的物理帧。CPU 只处理了 1 个描述符。

MTU 4200：你的程序构造 1 个 大的工作请求，网卡直接作为 1 个物理帧发送。CPU 还是只处理了 1 个描述符。

结论：只要数据量（4KB）在单次提交范围内，无论 MTU 是多少，CPU 做的功是一模一样的。
```


## 什么时候 MTU 会显著影响性能
### 软件角度(CPU角度)
当 pps （即CPU）是瓶颈时，通过调大MTU，可以减少PPS，即降低CPU使用，就可以提高性能。

#### 小包 flood
比如：64B packets 进行flood，此时网卡带宽不是瓶颈（带宽上不来），CPU是瓶颈。
通过将MTU调大，发送更大的数据包，可以降低PPS（减少CPU的使用），提高吞吐。

#### kernel TCP stack
kernel TCP stack 是 per-packet处理的 ，MTU调大，可以减少PPS数量。

### 硬件角度(网卡角度)
NIC pipeline 是瓶颈的时候，通过调大MTU，一次pipeline可以发送更多的字节数时。

#### streaming 大消息
发送的是超大的消息，拆分为多个数据包(比如N个)，从网卡硬件角度考虑，N个数据包无法并行发送时。
调大MTU之后，拆分后的M个数据包可以并行发送，或者即使不能并行发送，但是网卡硬件一次pipeline发送的字节数也比之前多时。

发送大消息的场景：
```bash
RDMA write
GPU AllReduce
storage IO
```

#### 多个cpu(线程)打流占满网卡时
多个线程(cpu) 进行任务下发，作为生产者；
网卡硬件发送数据，作为消费者。

网卡硬件是瓶颈时，MTU调大，网卡硬件一次pipeline发送更多的数据时。
