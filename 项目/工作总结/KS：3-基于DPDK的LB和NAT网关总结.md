## 基于业务的限速
### 背景
![](attachments/Pasted%20image%2020260411120227.png)

项目背景
	当前Kgw/Knat某个业务可能会短期内占用大量系统带宽，进而影响其他业务乃至整个系统的正常流量转发。所以需要一套基于VS(业务)粒度的限速模块。
	DPVS 原生的 QoS（TC） 是一个独立的模块，和 ipvs 负载均衡的功能没有任何联系，即和VS没有绑定关系，需要单独配置报文匹配规则（qos classify）、带宽限速参数和算法（qos sched）。 DPVS 原生 QoS cls 在数据面进行报文规则匹配时，一条一条规则进行顺序比较，直到完全匹配到规则，效率低下。
	所以对于新四层负载均衡的 VS 级别的限速需求，由于匹配规则条目非常多，规则匹配效率很低下，非常影响性能，是不能满足 VS 级别的众多 VS 时的限速需求的。
	所以需要自己重新开发了一套适合基于VS级别的 QoS 服务，提供：
		● VS 级别的 inbound、outbond 两个方向的 bps 限速；
		● VS 级别的最大并发连接数 max_conn 限速；

设计目标
	基于VS 的Qos 服务是嵌入进 dpvs 负载均衡处理流程的，支持单机 3000+ 量级的 VS 的各类限速，并且设计了一套配置命令，以及 VS 级别的各种统计。

功能目标
	单机支持基于vs的多种粒度的限速：
		VS 级别的 inbound、outbond 两个方向的 bps 限速；
		VS 级别的最大连接数max_conn 限速；
	平滑性/准确性：
		尽可能的限速精准；
		根据实时统计情况尽可能的平滑丢包，减少对业务的影响；

性能目标
	限速误差控制在5%左右；
	限速对于单机性能影响控制在5%左右；

### 分析

性能
	VS 级别 QoS 服务开发中的最大难点就在于 「QoS 多核处理」。如果是单纯的单核 qos 限速，其实普通令牌桶限速算法就已经足够。但由于 VS 级别 QoS 的每个 VS 中的各连接流量是在多核上同时运行的，所有业务流量的每个包要都进行限速操作。
	如果使用全局令牌桶，对全局令牌桶操作的 「cache 一致性」或者「加锁」都将严重消耗 cpu 性能，多核大流量下性能会受到严重影响。

准确度/平滑性
	准确度：
		在保证性能的情况下，QOS限速也需要尽可能的精准；
	平滑性：
		☐ 是否使用借贷模式优化平滑性？
		桶中只要令牌数只要大于0即可转发数据包，提前借贷的令牌在下个周期偿还；
		☐ 一个时间间隔的后段集中丢包的问题?
		时间段的前段有突发流量消耗掉所有令牌，后段无令牌可用而丢包；
		☐ 一个连接的首包是否丢弃问题?
		限速对于一条连接的首包不生效；
		☐ 重传数据包是否丢弃问题？
		限速对于tcp重传数据包不生效；

### 方案：单速率双桶 + 父子令牌桶
使用令牌桶流量测量方法进行QOS限速。
单速双桶算法的整体流程如下图所示:
参数：
	● CIR（Committed Information Rate）：
	承诺信息速率，表示向C桶中投放令牌的速率
	● CBS（Committed Burst Size）：
	承诺突发尺寸，表示C桶的容量
	● EBS（Excess Burst Size）：
	超额突发尺寸，表示E桶的容量
流程：
	● 系统按照CIR速率向桶中投放令牌：
	若Tc<CBS，Tc增加；
	若Tc=CBS，Te<EBS，Te增加；
	若Tc=CBS，Te=EBS，则都不增加。

	● 对于到达的报文，用B表示报文的大小：
	若B≤Tc，报文被标记为绿色，且Tc减少B；
	若Tc<B≤Te，报文被标记为黄色，且Te减少B；
	若Te<B，报文被标记为红色，且Tc和Te都不减少。
	
![](attachments/Pasted%20image%2020260411120248.png)

如果是所有的 worker（slave）线程 下的相同的Svc共享一个全局令牌桶，那么写者会随着Slave线程的增多而增多，不加锁的话，可能会导致限速不准确 以及 cache 一致性的问题；加锁的情况下，则会随着Slave线程个数的增多，导致锁的竞争激烈，影响性能以及扩展性。
可以考虑每个Slave线程对应一个子令牌桶，Master线程对应一个全局令牌桶。每个Slave线程从自身的小桶中消耗令牌，Master对应的大桶也会给Slave线程的小桶定期分发令牌；
这样对于每个Slave对应的子令牌桶中的令牌而言，最多2个线程进行写操作（Master定期分发令牌，Slave中数据包消耗令牌）。另外使用原子变量，在不加锁的情况下，尽可能的减少误差。


● 一个全局令牌桶
随着时间的推移，每次放入令牌仅仅放入全局令牌桶。为什么不放入线程令牌桶？假设需要限速的报文到了不同的线程，并且每个线程流量不同，那么对于每个线程放入令牌的数量就不得而知了。
全局令牌桶通过Master线程来维护，每次放入令牌的数量 = △t × CIR
△t是当前时间与上次添加令牌的时间之差，一般是cycles；
CIR 是承诺信息速率，表示向桶中投放令牌的速率；

● 每个线程拥有独立的子令牌桶
子令牌桶只消费令牌，不放入令牌。当子令牌桶的令牌不够时，全局令牌桶定期分发令牌给子令牌桶。某个时间段，子令牌桶获取的令牌数如下：
`每个子令牌桶获取的令牌数量 = 该线程收到报文所占比例*全局令牌桶中的令牌数`；

某个Slave线程收到数据包之后，会从子令牌桶中消耗一定的令牌，才会允许数据包的通过；对于Bps限速而言，数据包过桶的流程如下：
```bash
If 子令牌桶中令牌足够
	数据包过子令牌桶消耗的令牌数 = 数据包大小；
Else
	丢包
```

## 业务支持：KGW直通容器
### 背景
业务容器化是趋势，可以提高资源利用率。当前集群外访问容器化的业务需要经过kvr。kvr是容器虚拟网络的网关，基于x86服务器开发，带宽不大，跨集群访问容器，或者从物理机访问容器都需要经过kvr，很容易成为网络瓶颈。

对于业务方，从物理机迁移到容器中，仍然会有四层负载均衡的需求。如果KGW经过kvr转发到容器，网络路径长，可靠性会下降，网络延时也会增加，会给kvr的容量造成更多的压力。

KGW为容器提供四层负载均衡的另一个挑战是，容器的量比较大，且变更频率比较高，容器的迁移要求KGW联动变更，对配置变更的时效性有了更高的要求。生效慢的主要原因在KGW的keepalived组件性能差，代码架构不合理。

### 方案
![](attachments/image%20(23)%201.png)
KGW直通容器是通过封装VXLAN，通过三层网络路由，到达后端容器。
每个VS的RS需要配置VXLAN封装参数。同时keepalived健康检查的流量，也要进行VLXAN封装，检查VXLAN隧道的可用性。

![](attachments/image%20(24)%201.png)

### 成果
KGW改造后，可以直通容器，为容器化的业务提供LB服务。Kgw直通容器后，访问LB VIP的流量可以不经过kvr，降低kvr的负载，降低访问延时。

keepalived重构后，作为基础服务的kgw，配置变更不再依赖PCS服务。支持GRPC增量下发配置，配置变更时间从之前的秒级，降低到了10毫秒级。同时优化了go_keepalived内存使用和并发性能，可以支持10万量级的VS，100万量级的RS管理。

### 为什么没有用GRE隧道，vxlan隧道

【
      为什么没有用GRE隧道，vxlan隧道？？？
选择IPIP隧道是基于什么考虑？？
还有什么其他的隧道，GENEVE？？
】

  

IPIP：
配置简单。隧道包大小相对来说更小一些。

  

IPIP和GRE：
IPIP隧道相对于GRE隧道而言，基本没有什么区别，包含配置命令什么也都接近。就是GRE比IPIP多了一个GRE头，包大了一点吧。

  

IPIP和vxlan：
vxlan是一个二层的隧道，就是内层有一个完整的数据包，从二层，三层，到四层。vxlan隧道导致数据包就更大了。另外，vxlan内层是完整的，如果配置VIP，还需要再隧道口上开启ARP抑制。

  
GENEVE：
隧道头自定义，基于TLV格式，填充合适的内容。可能更友好，但目前IDC应该不支持。
比如：可以将内存的信息放入到GENEVE头中，然后网关就可以直接获取到内存的信息，进行转发了。

## conhash内存使用的优化
### 背景
![](attachments/Pasted%20image%2020260411121254.png)
![](attachments/Pasted%20image%2020260411121313.png)

背景
```bash
(1) 线上多个KGW集群存在资源利用率不足问题，但集群合并受限于单机性能不足「单机最大支持600W会话」
	春节重保期间单机会话容量达到90%水位
(2) 线上存量机器内存「64G」过小
(3) 原有conhash调度算法内存占用大：只支持3K+后端配置
	调度数据：Per-Core
	虚拟节点的Cache-line对齐，存在内存浪费
```


目标
```bash
利旧服务器：内存不变情况下，开发出一套高性能的conhash调度算法，提升单机性能
		「支持10W+ conhash的后端配置，1600W+ 会话」
```

### 方案

挑战
```bash
突破存量机器「64G内存」内存限制：支持10w+配置以及1600w+的会话数
新的Conhash调度算法在节约内存、高性能调度、业务配置变更时效之间的权衡
无损灰度：新老Conhash方案的兼容，业务流量的平滑稳定、无损
高扩展性：抽象一套可扩展的Conhash调度算法，支持多种Hash因子
```

![](attachments/Pasted%20image%2020260411121330.png)


整体思想：将大量占用内存的 per-core的调度 data -----> lock-free shared 调度data 
```bash
(1) 虚拟节点（大量占用内存）：
	无锁共享：
		lock-free ring: 传递虚拟节点数组给其他的worker线程
		refcnt-based reclam: 多线程下虚拟节点的回收
(2) 真实节点（少量占用内存）：
	per-lcore： 无锁调度真实节点（后端RS）
	快速查找：基于虚拟节点中索引O(1) 查找到真实节点
```

```bash
○ VS使用有序数组来保存RS的虚拟节点
○ 多个线程下的同名VS共享一份调度结构(有序数组)
○ 多个线程下的同名VS独占一个保存当前Core下RS地址的RS数组
```
收到数据包，调度选择RS时，基于数据包中提取hash因子，进行hash后在有序数组中二分查找，得到虚拟节点后，再基于虚拟节点中保存的真实节点的索引 rnode_index，在RS数组中得到VS下的RS。

# KNAT

## KNAT公网流量管理
### 背景
性能问题+成本问题+安全问题：
IDC内的服务器访问公网，是经过KNAT之后从BGP出口到公网的。这些请求的流量和公网业务合用BGP出口。之前公网访问几乎没什么限制(使用一个大的网段作为白名单，在大网段内的机器都可以出公网)，所有IDC服务器都可以自由访问公网。有安全风险，和成本问题(BGP出口成本相对比较高)。
在重大活动的时候，业务对公网出口带宽需求增大，需要根据业务优先级做保障，由于无使用限制，有造成出口拥塞的风险。


### 方案
（1）ACL性能问题：使用DPDK的ACL + 策略变更（增删白名单）时 单独线程编译ACL规则
之前版本的KNAT，使用使用链表管理，只能配置1k左右的策略（MathRule白名单），策略数再多，就会影响转发性能，造成延时丢包。没办法做到细粒度管控和流量展示。
KNAT对性能要求非常高，并且要求数据面转发延时低。同时ACL管控策略需要灵活支持源IP、目的IP、端口、网段，方便以后运维和管理。当前ACL策略是用链表管理和查找的，查找效率低，策略变更慢。

![](attachments/image%20(41).png)

本次开发使用DPDK的ACL库，保证查找性能高，转发效率高，延时低。
DPDK的ACL库，不支持增量更新，如果直接使用，策略变更（增删白名单）开销很大，会导致策略变更生效非常慢，影响数据面的流量转发。
为解决这个问题，使用单独线程异步编译ACL规则，控制面策略变更不阻塞。
同时使用了CAS机制，数据面转发线程通过指针引用ACL规则，编译线程重建ACL的B+树之后，更新指针。数据面转发线程可以无锁访问ACL的B+树，保证策略变更时，能高性能转发，没有额外延时等待。

（2）BGP带宽成本问题：边缘出口
如果要降低BGP出口成本，可以将KNAT流量调度到CDN边缘节点，可以进一步节省BGP出口的带宽成本。整体方案如下：出公网流量的SIP经过NAT设备后转换为边缘出口公网IP，在网络侧配置基于SIP的策略路由导流到边缘节点出去

![](attachments/image%20(40).png)


### 成果
对KNAT的流量进行了梳理，梳理出使用KNAT的服务器20万台，使用带宽量较大的产品线5个。经过SRE同学的治理，KNAT出口的峰值带宽从300G下降到了100G。
开发了新版本KNAT，支持策略数从1k，提升到60万，有能力对IDC全网服务器访问公网配置管控策略，并且可以实时展示每台服务器的带宽使用情况。
完成了KNAT流量调度到CDN边缘的方案设计和一期开发，正在上线。预计可以将BGP出口的KNAT流量降低到0。

### 流量如何导流到边缘

出去流量：流量经过SNAT之后，sip变为选择的边缘CDN出口的ip。然后在SNAT到边缘的链路上配置基于SIP的策略路由，导致到边缘（目前没有配置VXlan隧道封装）。

进来的流量：业务的响应的流量从公网进入到指定的边缘节点，在IDC内网以及边缘节点中，（CDN的sip）是通过SNAT发布出去的，因为会导流到对应的SNAT设备。

## LB软硬件一体化的问题
LB软硬件一体化实现

（1）优势：高带宽、低时延
软硬件一体化实现，转发能力强（单机12.8T）

（2）问题
可编程交换芯片的问题：
1》硬件的内存有限，可能只有百兆的级别，可存放的会话有限制。可能就是百万的级别，这个还是不考虑其他的配置。目前线上单机已经存在了1000w+的会话。
即从带宽这个角度来看，可编程转发芯片可以满足单机高带宽，但是从会话量这个角度来看看，可编程转发芯片还需要结合一些其他的优化技术来继续优化。

2》表项的下发速度问题：
软件生成会话，然后下发给硬件。这个表项的下发的速度问题。
可编程芯片最简单的逻辑就是基于规则转发，这个规则如果是上层下发下来的是最简单的。
如果是可编程芯片自己来生成这个规则，这个应该也可以做，但对于P4语言来实现的逻辑上，可能复杂了一些。

**思路**：软硬结合，识别大象流和老鼠流。大象流走硬件，老鼠流走软件。

(1) 模块组成：

### 整体流程

Fast PATH:  物理网卡收到包之后，匹配到硬件规则，直接基于硬件规则进行Fullnat转换，转发出去。

Slow PATH:  物理网卡收到包之后，没有匹配到硬件规则，则上送给ARM系统的KGW处理。如果是新建流量(如TCP的Syn)，则直接在ARM的KGW中进行新建并转发。后续将建立的长连接的Session信息下发给硬件。

Failover PATH：硬件中匹配不到规则，在ARM的KGW中也无法查询到Session会话，且流量不是新建报文，则将报文上送到Host中的KGW进行处理。

```bash
> （1）UDP如何处理？在ARM中查找不到，UDP都认为是新建，上送到 X86 KGW，而不是在ARM的KGW中处理？

> 因为升级ARM中的KGW过程中，X86的KGW中存在同步过来的UDP Session，本机的其他的DPU的ARM中KGW收到UDP报文，无法在ARM KGW中查找到会话，上送到Host KGW就可以查询到原本属于本机的会话。

> 另外，就是DPU中的ARM子系统的内存相对较小，Session容量有限，UDP超时时间较长，使用Host KGW存储大量的udp session。

  

> （2）对于新建流量，是否也存在上送呢？

> 由于DPU中的ARM核数有限，如果ARM中的KGW的CPS/并发连接数达到一定阈值，也可以考虑上送到Host KGW.

  

> （3）Host的KGW收到转发流量也无法查询到会话，怎么办？

> 这种情况发生在，比如集群的KGW机器扩缩容的情况，此种情况，可能需要在Host KGW之间进行Session同步或者建立集中式的KV Session 集群。如下所示，先不考虑此中情况。

  

> （4）硬件中的Fullnat规则和ARM KGW、Host KGW中的会话的一致性？

> 对于连接新建、连接销毁的流量都需要上送到ARM KGW。KGW中新建的长连接规则下发到硬件，会话销毁时同步删除硬件中的规则。

> 对于长连接，则ARM KGW定期从硬件中获取规则的统计信息，决定是否更新自身的Session超时时间。
```


### 版本升级/扩缩容

版本升级如下的Session同步所诉，见下。

对于机器的扩缩容，如果只在本机的HOST的KGW以及本机的ARM的KGW之间进行Session同步是不够的，需要要建立集中式的Session的KV集群或分布式的多副本「即每个KGW承载整个集群的Session」来进行处理了。

> 注：为了简化方便，先不考虑机器机器的扩缩容的情况。可以在二期再进行考虑。
> 后续如果考虑，可能需要考虑使用一个KV「Key-value」的机器，存储所有KGW服务器上的Host KGW的会话信息。
> HOST上的KGW收到流量，先本地查询，如果查询不到，则考虑从KV 服务器中查询。
> 对于TCP新建：本地查询不到，直接本地新建。不需要去KV查询。
> 对于TCP ACK：先本地查询，本次查询不到，去KV查询。KV中也查询不到，则丢弃。
> 对于UDP：先本地查询，本地查询不到，去KV查询，KV中也查询不到，则直接本地新建。


### Session同步

KGW进行版本升级时，则可能导致流量断开。为了保证长连接不断连，需要进行Session同步。

先升级DPU中的KGW，待DPU中的KGW升级完成，再进行本机Host上的KGW的升级。


预期目标：
同步范围是单个KGW设备中的DPU KGW和Host KGW之间。
以Virtual Server为粒度配置是否同步；
提供一个可配的时间阈值来决定一个会话同步的时间，该阈值和VIrtual Server的开关同时开启才会生效。
同步后的备会话要根据主会话持续的更新状态，包括超时时间更新、会话超时等；
基于包粒度进行Session的分发，单个Pkt中包含某个worker的一个链表中的多个Session信息。

  
可运维性:
需要能提供一种能够快速关闭和开启会话同步的功能，以快速解决会话超阈值或者恢复同步的情况；
需要提供一种接口，能够在短时间内做全量的同步会话，以解决设备短时间内下线上线的场景。
要提供一种debug机制，能够查看会话是否被同步、同步状态。


Session同步模块：
Session发送发：ssender, worker处理线程中一个子逻辑，实时或者批量的发送本地需要同步的Session到sync线程上。
Session中继站sync线程：将收到的同步数据包分发到其他KGW上，实现类似组播的功能。
Session接收方 SReceiver：接收sync发来的同步Session数据包，并创建Session。

![](attachments/image%20(34).png)


```bash
> (1) DPU 中的KGW升级：

> 升级之前，需要将自身的Session信息，全量同步给本Host中的KGW，升级完成之后，再从本Host的KGW中拉取属于本DPU的Session。

  

> (2) Host中的KGW升级：

> ARM中的KGW升级完成之后，再升级Host中的KGW；如果ARM中的内存足够，也可以考虑将Host的KGW中自身独有的Session再分发到本机的各个DPU的ARM KGW中。

> 在Host的KGW升级过程中，原本匹配Host KGW中的session的流量，可能Ingress流量到达本机的DPU1，egress流量到达本机的DPU2。

> 待Host中的KGW升级完成之后，需要从本机的各个DPU中拉取属于自身的Session。

  

> （3）同步Session的刷新、超时、删除等

> 存在Session同步，则需要考虑不同设备上的会话信息的删除、超时、刷新等等。

  

> （4）常态下是否进行同步？

> 为了简化，不考虑常态下的增量同步；

> 只有在升级KGW的时候，进行全量同步；升级完成之后，再次进行全量拉取。这样，对于同步Session的超时、删除、状态更新相对简单一些。

> 至于增量同步，可以在二期再进行考虑。

  

> (5) X86 Host  KGW 和 Arm KGW的worker个数可能不一样？

> Session同步要求Host  KGW 和 Arm KGW的worker个数相同。另外，ARM KGW和X86 kgw的 worker线程个数都是2的N次方。

> 因为，Host KGW正常情况下的转发流量相对较小「UDP流量、Session同步流量、升级过程中failover到自身的TCP转发流量等」，因此 Host KGW的性能保持和ARM KGW的性能相同也是可以理解的。
```

### 路由策略

当前的KGW的路由，只在wan口发布了VIP，对于LIP都是物理网络静态配置的。如果要进行Session同步，则需要Wan口发布VIP，Lan口发布LIP。

  

> (1) LIP 路由的发布？

> 总结就是区分LIP的粗细路由进行发布。具体就是：

> 每个KGW服务器，需要将本机的Host KGW的LIP以及DPU ARM KGW的LIP都发布出去，发布的是大的网段的路由。

> 本机的Host KGW的LIP以及DPU ARM KGW分别再发布属于自身的LIP。

> 注：【暂不考虑集中式的KV Session存储集群】如果存在集中式的KV Session存储集群，即需要每个KGW服务器发布整个集群的LIP的网段的粗路由和自身的细路由。

  

### 软硬件规则

> (1) 硬件规则包含：

> DPU中的Fullnat转发规则：快速转发路径。

> 网卡的RSS以及FDIR规则：保证同一条流的正反向交给KGW的同一个Core 进行处理，KGW中的Session信息是Per-core的。

> （2）会话同步时，流量匹配同步会话的问题？

1. > 同步会话的消息，将同步的会话在新的KGW的某个线程1中建立
    
2. > 流量的正向报文通过网卡的RSS无法将报文Hash到线程1「有可能是Host KGW和ARM KGW的线程数不同，或者网卡的RSS Hash不同等原因」
    
3. > 流量的反向报文通过网卡的FDIR规则无法将报文导向指定的线程1「比如：Host KGW的网卡中不存在 ARM KGW的 FDIR规则，或者 线程数不同等」
    

> 对于以上问题，尽可能的通过硬件规则的设置，保证流量的正反向「正向RSS，反向FDIR」报文可以在接收包的线程中，可以匹配到同步后的会话。如果无法匹配到，则考虑软件实现RSS以及FDIR来查询正确的线程，然后进行redirect到正确的线程来处理。

# 经验和难点
## 最大的挑战
最大的挑战，还是稳定性这一块吧，集群合并，多个业务融合，如何保证稳定性。
说一下其中的一个问题吧，就是踩内存的问题：
- 1》影响
这个问题

1.1》在社区
出现了至少3年，我来快手的时候就有了，期间社区也多次有人提到，但是一致没有解决。

1.2》在公司
在公司的线上也出现了几次这个问题导致的程序coredump。

- 2》难点：
2.1》问题难以复现
2.2》定位方向容易走偏
本质上是一个踩内存的问题，实际上从表项上看又是一个内存的重复释放的问题。然后踩内存呢，又是一个特殊的踩内存，不像是那种内存写越界这些，它是一个结构体中的中间的字段被踩了，并且是特定的偏移量的位置，两端的数据都是正常的。
并且这样的结构体变量是动态申请，释放的，存在成千上万个。

2.3》缺少工具
KGW/KNAT是这种DPDK程序，就是bypass kernel的用户态程序，直接从网卡取包处理，像一些内核提供的工具是没法用的。
不像普通的基于Linux内核的用户态程序，可以通过一些工具，比如mprotect, address sanitizer 来定位踩内存。DPDK没法用这样的工具。

- 3》做了什么
3.1》复现脚本
就写了一套脚本，大量配置增删改查的同时，同时打流。最终复现了。

3.2》自己写了一个检查的工具
就是写了一些检查的线程，结构体中添加一些魔数字段，检查线程一致检查结构体的对应字段是否发生改变，一旦发生改变，就把程序给杀了。
产生coredump之后，基于coredump的其他线程的调用堆栈，一点点分析；因为是其他的线程刚刚裁过内存，通过分析上下文以及被踩的地址，运气好的话应该也可以分析出来。

- 4》经验推广、工具
首先是稳定复现，然后就是对于dpdk这种程序，就是通过自己编写工具，比如开启几个检查线程，死循环的来进行检查。
