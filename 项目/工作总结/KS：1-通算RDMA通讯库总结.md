## Preload一键替换
### Preload一键替换和ZC的矛盾
传统的 socket编程的，`read/write` 都是需要拷贝的；
如果想要ZC，就需要提前注册内存给DMA + 添加回调函数(`read_done_cb, write_done_cb`)。

因此，Preload一键替换原始的基于内核的socket接口，和ZC之间是矛盾的。

### 小结
#### 方案一： preload一键替换但允许copy
#### 方案二：高性能ZC但无法无感知替换

## 上层业务使用协程 和 UCL库的兼容

传统模式下，**协程是“用户态的轻量级线程”**。

### 业务使用协程时，传统网络代码是什么样
很多业务已经使用协程库，例如：
```bash
- go coroutine
- libco
- boost coroutine
- C++20 coroutine
```

在业务开发中，协程（如 Go 协程、libco、Python asyncio）的核心价值是==业务侧用同步的方法写代码（代码写起来简单，可读性强）， 底层异步 IO实现==，避免传统多线程的上下文切换开销，同时解决回调嵌套的 “回调地狱” 问题。


#### 协程和线程以及回调对比

|模式|代码写法|IO 等待方式|并发承载能力|性能开销|
|---|---|---|---|---|
|多线程|同步|线程阻塞（内核态切换）|百 / 千级|内核上下文切换（~10us）|
|纯回调|异步嵌套|无阻塞（回调驱动）|万级|代码复杂度高|
|协程|同步|协程挂起（用户态切换）|十万 / 百万级|用户态切换（~1us）|

注：
```bash
一个线程上，可以起多个协程, 并且相互独立，互不影响；
各个协程之间从宏观上看，是可以并行的；
协程从挂起到唤醒，是在用户态的切换。
```

#### go协程网络通信范例
Go 协程是业务中最主流的协程网络模型，其网络库（`net`包）底层基于 epoll/kqueue 实现异步 IO，上层封装为同步接口：
```go
// 业务代码（同步写法，底层异步IO）
func handleConn(conn net.Conn) {
    defer conn.Close()
    buf := make([]byte, 4096)
	// 1. 看起来是阻塞读取 
	// 实际上：如果数据没到，当前协程挂起，CPU 去跑其他协程
    n, err := conn.Read(buf)
    if err != nil {
        return
    }
    // 2. 业务处理（同步逻辑）
    data := processData(buf[:n])
	// 3. 看起来是阻塞写入 
	// 实际上：如果发送缓冲区满，当前协程挂起，等待可写事件
    _, err = conn.Write(data)
    if err != nil {
        return
    }
}

func main() {
    listener, _ := net.Listen("tcp", ":8080")
    for {
        // 接收连接，每个连接启动一个协程
        conn, _ := listener.Accept()
        go handleConn(conn) // 协程并发，无线程创建开销
    }
}
```


如果是C语言的风格，如下所示：
```c

void handle_request(coroutine_ctx_t *ctx) {

    // 实际上：如果数据没到，当前协程挂起，CPU 去跑其他协程

    log_info("request handled");
```

==协程就是业务层同步写法+ 底层异步 IO实现==。

**（1）业务层同步写法**：
业务开发人员看到的代码是**线性、同步、阻塞式**的。他们不需要关心 `epoll`、回调地狱或状态机。

**（2）底层异步 IO实现**：
当业务调用 `co_read` 时，底层发生了什么？

1. **拦截/封装**：`co_read` 内部调用标准的 `recvmsg` (非阻塞模式)。
2. **判断就绪**：
    - 如果数据已到达：直接返回数据，协程**继续执行**。
    - 如果数据未到达 (`EAGAIN`)：
        - **保存现场**：保存当前协程的栈指针 (SP) 和程序计数器 (PC)。
        - **注册事件**：向调度器注册“当 FD X 可读时，唤醒协程 Y”。通常底层依赖 `epoll`。
        - **协程挂起 (Yield)**：当前协程主动让出 CPU，切换到调度器。
3. **事件循环 (Event Loop)**：
    - 主线程运行 `epoll_wait`。
    - 内核通知某 FD 可读。
    - 调度器找到对应的协程 Y，将其状态改为“就绪”。
4. **协程恢复 (Resume)**：
    - 调度器再次轮到协程 Y，恢复栈和 PC。
    - `co_read` 函数从“挂起点”醒来，再次调用 `recvmsg`（此时一定有数据），返回结果。
    - 业务代码继续向下执行。

```bash
+-----------------------+
|   协程调度器循环      |
+-----------------------+
          |
          v
+-----------------------+
| 1. 检查就绪队列       |
|    (有可运行的协程吗？)|
+-----------------------+
      |           |
      | YES       | NO (所有协程都在等 IO)
      v           v
+------------------+  +---------------------------+
| 2. 执行协程      |  | 3. 调用 epoll_wait(timeout)|
|    (Run Co)      |  |    (CPU 阻塞/睡眠)        |
+------------------+  +---------------------------+
      |                           |
      | (协程 yield/结束)         | (内核通知: 数据到了)
      v                           v
+-----------------------+  +---------------------------+
| 回到步骤 1            |  | 4. 唤醒对应协程 -> 入队   |
+-----------------------+  +---------------------------+
                                   |
                                   v
                            +-----------------------+
                            | 回到步骤 1 (现在 YES) |

注：通常会在每次 `yield`（协程挂起） 后，或者每运行 N 个协程后，强制插入一次 `epoll_wait(timeout = 0)`，以保证网络IO不会因为多个长计算任务而饿死。比如，有1000个协程，只有一个协程在等待IO。
```

#### 协程框架封装底层IO多路复用
协程框架（如 Go runtime、libco）会封装底层 IO 多路复用（epoll/select），核心流程：

（1）协程调用`Read/Write`时，框架将 IO 请求注册到 epoll，并**挂起当前协程（suspend coroutine）**（用户态操作，无内核切换）；
> 注：实际上协程 runtime 会把 阻塞 IO 变成 yield，一个协程挂起，调度器运行别的协程。

（2）内核通过 epoll 通知 IO 就绪后，框架**恢复对应的协程（coroutine coroutine）**，协程从挂起点继续执行；

（3）整个过程中，承载协程的线程（M/P 线程模型）不会阻塞，可调度其他就绪协程，最大化 CPU 利用率。
