# 概述
在Linux中主要提供了`fork`、`vfork`、`clone`三个进程创建方法。 在linux源码中这三个调用的执行过程是执行`fork(),vfork(),clone()`时，通过一个系统调用表映射到`sys_fork(),sys_vfork(),sys_clone()`,再在这三个函数中去调用`do_fork()`去做具体的创建进程工作。

## fork的原理
### 写时复制(COW：copy on write)

默认 `fork` 行为 (COW)：
- **页表复制：** 父进程页表中的 VMA 被复制到子进程。
- **物理页共享：** 父子进程的页表都指向相同的物理页。
- **权限设置：** 共享的物理页被设置为 **只读**。
- **目的：** 实现 **写时复制 (COW)**。父进程或子进程的第一次写入操作会触发页故障，内核复制物理页，从而保证各自的内存独立性。

#### 为什么需要写时复制

第一代Unix系统实现了一种傻瓜式的进程创建：当发出fork()系统调用时，内核原样复制父进程的整个地址空间并把复制的那一份分配给子进程。这种行为是非常耗时的，因为它需要：
- 为子进程的页表分配页帧
- 为子进程的页分配页帧
- 初始化子进程的页表
- 把父进程的页复制到子进程相应的页中

这种创建地址空间的方法涉及许多内存访问，消耗许多CPU周期，并且完全破坏了高速缓存中的内容。在大多数情况下，这样做常常是毫无意义的，因为某进程fork出一个子进程后，其子进程仅仅是为了调用exec执行另一个可执行文件，那么在fork过程中对于虚存空间的复制将是一个多余的过程，这样就完全丢弃了所继承的地址空间。

#### 设计理念
如果有多个呼叫者(callers)同时要求相同资源，他们会共同取得相同的指标指向相同的资源，直到某个呼叫者(caller)尝试修改资源时，系统才会真正复制一个副本(private copy)给该呼叫者，以避免被修改的资源被其他呼叫者直接察觉到，这过程对其他的呼叫只都是通透的(transparently)。
此作法主要的优点是如果呼叫者并没有修改该资源，就不会有副本(private copy)被建立。


#### 什么是写时复制

但由于现在Linux中是采取了`copy-on-write(COW写时复制)`技术，为了降低开销，fork最初并不会真的产生两个不同的拷贝，因为在那个时候，大量的数据其实完全是一样的。写时复制是在推迟真正的数据拷贝。
若后来确实发生了写入，那意味着parent和child的数据不一致了，于是产生复制动作，每个进程拿到属于自己的那一份，这样就可以降低系统调用的开销。所以有了写时复制后呢，vfork其实现意义就不大了。

即：没有数据变更之前，父进程和子进程共享页帧而不是复制页帧。只要页帧被共享，它们就不能被修改，即页帧被保护。无论父进程还是子进程何时试图写一个共享的页帧，就产生一个异常，这时内核就把这个页复制到一个新的页帧中并标记为可写。原来的页帧仍然是写保护的：当其他进程试图写入时，内核检查写进程是否是这个页帧的唯一属主，如果是，就把这个页帧标记为对这个进程是可写的。
```bash
当进程A使用系统调用fork创建一个子进程B时,由于子进程B实际上是父进程A的一个拷贝,
因此会拥有与父进程相同的物理页面.为了节约内存和加快创建速度的目标,fork()函数会让子进程B以只读方式共享父进程A的物理页面.
同时将父进程A对这些物理页面的访问权限也设成只读.

这样,当父进程A或子进程B任何一方对这些已共享的物理页面执行写操作时,都会产生页面出错异常(page_fault int14)中断,
此时CPU会执行系统提供的异常处理函数do_wp_page()来解决这个异常.

do_wp_page()会对这块导致写入异常中断的物理页面进行取消共享操作,为写进程复制一新的物理页面,使父进程A和子进程B各自拥有一块内容相同的物理页面.
最后,从异常处理函数中返回时,CPU就会重新执行刚才导致异常的写入操作指令,使进程继续执行下去.
```

总结就是：
```bash
（1）父子进程初始共享物理内存。
（2）仅在写入时复制数据，减少冗余拷贝/无意义拷贝。
```

#### fork之后，子进程exec 对 COW 关系的影响
##### exec 的作用

**(1)销毁 VMA：** 
exec 系列函数的作用是**用一个新的程序映像（executable image）替换掉当前进程的地址空间**，包括代码、数据、堆和栈等。
`exec` 会销毁当前进程（即刚创建的子进程）地址空间中的**所有**用户态内存映射（Virtual Memory Areas, VMA），包括所有通过 `fork` 继承自父进程的内存页表项。 随后，它加载新程序的代码和数据。

**(2)解除 父子进程的COW：** 
当子进程调用 exec 时，它会**丢弃**（或取消映射）原来从父进程 fork 过来、并正在 COW 机制下共享的所有内存页。取而代之的是，它会为新加载的程序分配和设置全新的内存空间。
- 在内核层面，这是通过减少这些共享物理页的**引用计数**（reference count）来实现的。由于子进程不再引用这些页，这些页的引用计数会相应减少。
- 对于所有原本共享的、且现在只有父进程引用的内存页，它们的引用计数会降为 1。此时父进程就不在有COW了，可以直接写，不会存在物理内存的拷贝。

##### 子进程调用 exec 后父进程写入行为

子进程调用 exec 后：

1. 父进程再进行写操作时，将不再触发 COW 机制（即不会发生物理内存复制）。
2. 这是因为在 exec 之后，父进程是这些内存页的唯一拥有者（引用计数为 1）。
3. 内核会解除这些页的“只读”保护标志，允许父进程直接写入，就像进程从未 fork 过一样。


#### 小结
COW 确保了只有在父子进程**真正需要修改**各自数据时才进行复制，而 exec 则确保了对于这种“**fork 后立即替换程序**”的常见场景，旧程序的内存复制开销为零。

fork 后面紧跟 exec 是 Unix/Linux 系统启动新程序（如 Shell 执行命令）的**经典模式**，COW 机制是这种模式能**高效运行**的关键：

|**阶段**|**进程行为**|**内存状态**|**效率提升**|
|---|---|---|---|
|**$\text{fork}$**|子进程创建|父子进程共享页，标记为只读 ($\text{COW}$)|避免了 $\text{exec}$ 马上就要丢弃的内存的**不必要复制**。|
|**$\text{exec}$**|子进程加载新程序|子进程丢弃旧页，解除父进程页的共享|父进程对自己的内存恢复独占写入权，**避免了 $\text{COW}$ 触发的写时复制**。|

## fork的特点
### 写时复制
**写时复制（COW）**：父子进程共享物理内存，仅在修改时分配新内存，避免冗余拷贝以及无意义拷贝。

在fork之后，子进程和父进程都会继续执行fork调用之后的指令。
**子进程是父进程的副本。它将获得父进程的数据空间，堆和栈的副本，这些都是副本，父子进程并不共享这部分的内存。也就是说，子进程对父进程中的同名变量进行修改并不会影响其在父进程中的值**。
但是父子进程又共享一些东西，简单说来就是程序的正文段。正文段存放着由cpu执行的机器指令，通常是read-only的。

```bash
当fork刚刚创建好子进程时，父子进程用的是相同的物理空间（内存区），子进程的代码段、数据段、堆栈都是指向父进程的物理空间；
也就是说，两者的虚拟空间不同，但其对应的物理空间是同一个。

同时，相关内存页被标记为只读，无论父子进程对其进行的首次写入操作，都会触发page fault，进而会重新分配内存页，进行内存拷贝，然后谁触发的写操作，就更新谁的进程页表。

如果任一进程写入一个 COW（写时复制）页，就会触发一个 页故障（Page Fault）。
在页故障处理程序中，如果这个页理应是可写的，内核会执行以下操作：

4. 分配一个新的物理页（physical page）。
5. 执行一次内存复制操作（`memcpy(newpage, shared_page, pagesize)`），将共享页的内容复制到这个新页中。
6. 然后，更新触发故障的那个进程的 页表（Page Table），将该虚拟地址映射到这个新分配的物理页上。
7. 随后返回用户空间，让存储指令（store instruction） 重新执行。


对于像 `fork` 这样的系统调用来说，这是一个优势，因为子进程通常会立即进行 `execve` 系统调用，在此之前它可能只接触（写入）了大约一个页（通常是栈内存的顶部）。
`execve` 会销毁该进程的所有内存映射，实际上是用一个新程序替换了它。这样，父进程再次成为所有页面的唯一拥有者。
（当然，已经设置为写时复制的页面除外，例如，使用 `mmap` 分配的内存通常是 COW 映射到一个全零的物理页，这样读取时可以命中 L1 数据缓存）。

一个聪明的优化是，`fork` 实际上可以预先复制 包含栈顶的那个页面，但对所有其他页面仍保持延迟的 COW 机制。
这样做是基于这样的假设：子进程通常会立即执行 `execve`，从而丢弃对所有其他页面的引用。
不过，即使有这个优化，在父进程中临时将所有页面设置为只读，然后又改回去，仍然会带来 TLB 失效（TLB invalidation）的开销。
```

### fork一次调用两个返回值
fork()调用执行一次返回两个值，对于父进程，fork函数返回子程序的进程号，而对于子程序，fork函数则返回零，这就是一个函数返回两次的本质。

在fork之后，子进程和父进程都会继续执行fork调用之后的指令。子进程是父进程的副本。它将获得父进程的数据空间，堆和栈的副本，这些都是副本，父子进程并不共享这部分的内存。也就是说，子进程对父进程中的同名变量进行修改并不会影响其在父进程中的值。但是父子进程又共享一些东西，简单说来就是程序的正文段。正文段存放着由cpu执行的机器指令，通常是read-only的。

### 独立性
父子进程代码共享，数据独立（修改互不影响）

#### system

### 间接依赖 `fork` 功能的函数族：`fork+exec+wait`
`fork` 及其后续的 `exec` 函数族是 **进程生成** 的基础模式。所有需要 **创建和运行另一个独立程序** 的高级接口，都离不开这一底层机制。

#### `exec` 函数族 (`execl`, `execv`, `execle`, `execve`, etc.)
用一个新的程序替换当前正在运行的进程的内存空间、代码和数据，但 **不创建新进程**（保持 PID 不变）。
##### `exec` 函数族与 `fork` 的关系
虽然 `exec` 本身不调用 `fork`，但它们通常是 **配对使用** 的。在执行新程序时，标准做法是：

- **`fork()`**：创建一个子进程。
- **子进程调用 `exec()`**：将自己变成新的程序。
- **父进程调用 `wait()`**：等待子进程完成。

因此，任何设计用于启动外部程序的函数（如前述的 `system()` 和 `popen()`）都会将 **`fork` + `exec`** 封装在一起。


#### 各种 守护进程（Daemon）启动脚本和工具
虽然不是直接的 glibc 函数，但许多高级的进程管理工具或脚本（如 `init`、`systemd`、`supervisord` 等）在启动新的服务时，其底层逻辑都包含 `fork` + `exec` 的步骤。

### 应用场景
#### bash中执行命令

当我们在 Linux 下的 `bash` 下输入一个命令执行可执行程序时，`bash` 进程会调用 `fork()` 创建一个新的进程，然后新的进程调用 `execve`系统调用来执行指定的可执行程序。

##### shell脚本中，每个命令的执行都是开启一个新的bash吗？
Shell 脚本中的命令执行可以分为以下几种情况：

**（1）内部命令 (Built-in Commands)/内置命令：不会开启新进程。**

- **定义：** 内部命令是 Shell 自身的一部分，它们由 **当前正在运行的 Shell 进程** 直接执行。
- **示例：** `cd` (改变目录)、`echo` (输出)、`read` (读取输入)、`export` (设置环境变量)、`test` (`[`/`]]`)、`source` (`.`) 等。
- **优势：** 执行速度极快，且能够直接影响当前 Shell 的状态（例如 `cd` 可以改变当前 Shell 的工作目录）。

**（2）外部命令 (External Commands)：会开启一个新的子进程 (Sub-process)，但不是一个新的独立的 Bash 实例。**

- **定义：** 外部命令是存储在文件系统中的 **可执行文件**（如 `/bin/ls`, `/usr/bin/find`, `/usr/bin/python` 等）。
    
- **执行方式：** 当 Shell 执行外部命令时，它会使用 **`fork()`** 系统调用创建一个 **子进程**，然后子进程使用 **`execve()`** 系统调用加载并执行那个外部可执行文件。
    
- **执行体：** 这个子进程执行的程序是命令本身（例如 `ls`），**而不是**一个新的 Bash 实例。==只有当你明确在脚本中调用 `/bin/bash` 或 `sh` 时，才会开启一个新的 Shell 进程==。
    
- **环境隔离：** 子进程会继承父 Shell 的环境，但它对环境变量和工作目录的改变 **不会** 影响父 Shell。

**（3）使用管道和命令替换**
**管道 (`|`)**：管道连接的每个命令通常都会在单独的子进程中执行。例如，`command1 | command2` 会创建两个子进程。
**命令替换 (`command`  或 `$(command)`)：** 括号内的命令会在一个 **子 Shell 进程** 或 **子进程** 中执行，以捕获其输出。



|**命令类型**|**是否开启新进程？**|**开启什么？**|**例子**|
|---|---|---|---|
|**内部命令**|**否**|当前 Shell 进程内部执行|`cd /tmp`, `export VAR=1`|
|**外部命令**|**是**|**命令本身的子进程** (如 `ls`, `awk`)|`ls -l`, `grep pattern file`|
|**明确调用**|**是**|**一个新的 Shell 进程**|`bash another.sh`, `sh -c 'cmd'`|



### 小结

任何需要 **在当前进程之外启动一个独立的、可执行的程序** 的 C 库函数或系统接口，其底层几乎都离不开 `fork` (或 `vfork`/`clone`) 来创建新的进程实体，再结合 `exec` 来加载新的程序代码。

## fork和clone的对比
### 对比

|**特性**|**fork (创建进程)**|**clone (创建线程/定制执行流)**|
|---|---|---|
|**主要目标**|**创建子进程**（Process）。|**创建线程**（Thread）或定制化的进程。|
|**地址空间**|**复制** 父进程的地址空间（**写时复制，Copy-on-Write**）。|**共享** 父进程的地址空间（默认行为）。|
|**进程 ID (PID)**|子进程获得 **新的、独立的 PID**。|子进程/线程获得 **新的 PID**，但在内核中与父进程属于同一 **线程组 ID (TGID)**。|
|**资源共享**|默认情况下，**不共享** 内存、文件描述符等（除了 CoW）。|可以通过参数（如 `CLONE_VM`, `CLONE_FS`）**精确控制共享** 哪些资源。|
|**性能**|创建开销较大（需要复制页表和内核数据结构）。|创建开销较小（只需设置新的执行栈和少量内核结构）。|
|**典型用途**|启动一个**完全独立**的新程序（如 `system()` 或 Web 服务器处理请求）。|**多线程编程**（如 `pthread_create()` 的底层实现）。|
|**系统调用**|`fork()` 或 `vfork()`。|`clone()`。|

### 使用场景
#### 什么时候使用fork
使用 `fork` 的核心原则是：你需要创建一个新的、完全独立的工作单元，它不应干扰或被父进程的内存操作所干扰。

**（1）执行外部程序（Process Isolation）：** 
当你希望创建一个子进程来执行一个完全不同的可执行文件时（通常结合 `exec` 使用），例如：
- 开启一个新的Shell，在其中执行命令。
- Web 服务器为每个客户端请求启动一个独立的服务进程。
- 调用 `system()` 或 `popen()`。

**（2）故障隔离（Fault Isolation）：** 
进程之间拥有独立的内存空间，一个进程的崩溃不会导致另一个进程崩溃。如果你需要高度的健壮性和隔离性，应使用 `fork`。
    
**（3）写时复制（CoW）：** 
`fork` 实现了高效的 写时复制。如果子进程主要用于读取数据，那么开销很小；只有当任一进程开始写入时，操作系统才会复制该页面，这对于创建进程后立即调用 `exec` 的场景（大部分情况）非常高效。


#### 什么时候使用clone
使用 `clone` 的核心原则是：你需要创建多个执行流来协同工作，它们需要高效地访问和共享同一块内存数据。


**（1）多线程编程（Threads）：** 
这是 `clone` 最常见的用途。在 Linux 中，线程本质上是共享了大部分资源的特殊进程。`pthread_create()` 就是调用 `clone()` 并传入特定参数（如 `CLONE_VM` 共享内存空间）来实现的。
- **优点：** 线程间切换开销小，通信（共享内存）效率高。


**（2）容器技术：** 
现代容器技术（如 Docker）也大量依赖 `clone` 系统调用，通过各种 `CLONE_*` 标志位来创建新的 命名空间 (Namespace)，从而实现文件系统、网络、用户 ID 等资源的隔离。

**（3）定制化的执行流创建**
`clone` 提供了大量的标志位（flags），让你能够精确控制子执行流要共享父进程的哪些资源，这适用于实现一些特殊需求：
