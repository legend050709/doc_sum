
## 进程的常见六种状态
常见的六种状态：**Running/Sleeping/Disk sleep/Stopped/Zombie/Traced**

在 Linux 操作系统中，进程的状态可以分为以下完整的分类：

1. Running（**TASK_RUNNING**：运行）：进程正在执行或准备执行。在多核系统上，多个进程可以同时处于运行状态。
    
2. Sleeping（睡眠）：进程暂时被挂起，等待某个事件的发生。这包括等待 I/O 操作完成、等待信号量、等待定时器等。睡眠状态又可以分为可中断睡眠和不可中断睡眠两种情况。
    
    - 可中断睡眠（S状态：Interruptible Sleep）：进程在等待某个事件时，可以被信号中断并唤醒。例如，当进程等待读取磁盘数据时，如果接收到一个中断信号，进程可以被唤醒并执行其他操作。
        
    - 不可中断睡眠（D状态：Uninterruptible Sleep）：进程在等待某些事件发生时，不会被信号中断。这通常是因为进程在执行一些关键的操作，如等待磁盘上的数据完全加载到内存中。在不可中断睡眠状态下，进程无法响应中断信号。
        
3. Stopped（停止）：进程暂停执行，直到接收到一个特定的信号才能继续执行。常见的例子是通过调试器将进程设置为停止状态，以进行调试操作。
    
4. Zombie（僵尸）：进程已经终止，但其退出状态仍然保留在进程表中，直到父进程调用 `wait()` 系统调用来获取子进程的退出状态。僵尸进程不占用系统资源，但需要父进程对其进行清理，否则它们会一直保留在进程表中。
    
5. Traced（跟踪）：进程被其他进程（跟踪进程）跟踪，跟踪器可以监视和控制跟踪进程的执行。
    
这些状态涵盖了进程在 Linux 中的所有可能状态。通过监视进程的状态，可以了解进程的执行情况和可用性，并对系统进行故障排查和性能优化。



## Stopped状态
向一个进程发送 `SIGSTOP` 信号，它就会因响应这个信号变成暂停状态（Stopped）；
再 向它发送` SIGCONT` 信号，进程又会恢复运行（如果进程是终端里直接启动的，则需要你 用 fg 命令，恢复到前台运行）。

### 怎样让一个进程进入`中止状态`
举个例子，假设程序在运行过程中，现在要求用户输入，而有些时候，用户并不想立即输入，这时用户可以通过`control + z`的键盘组合键来中止这个输入的操作，让这个进程变成`中止状态`：
```c
[root@localhost ~]# cat input.c
#include <stdio.h>

int main(void){
  int num = 0;
  printf("Input a number: ");
  scanf("%d", &num);


  printf("Number is %d\n", num);
  return 0;
}
[root@localhost ~]# gcc -o input input.c
[root@localhost ~]# ./input
Input a number:
```

中止前进程状态：
```c
[root@localhost ~]# ps -aux | grep input
root      7608  0.0  0.0   4220   356 pts/0    S+   11:20   0:00 ./input
```

键入`control + z`后再查看进程状态：
```c
[root@localhost ~]# ./input
Input a number: ^Z
[1]+  已停止               ./input
[root@localhost ~]# ps -aux | grep input
root      7608  0.0  0.0   4220   356 pts/0    T    11:20   0:00 ./input
```

通过`fg`命令恢复进程状态：
```c
[root@localhost ~]# fg
./input
123
Number is 123
```
## Traced 状态
当使用了`ptrace`跟踪后，所有发送给被跟踪的子进程的信号(除了`SIGKILL`)，都会被转发给父进程，而子进程则会被阻塞，这时子进程的状态就会被系统标注为`TASK_TRACED`，而父进程收到信号后，就可以对停止下来的子进程进行检查和修改，然后让子进程继续运行。

### gdb 调试使进程进程跟踪状态
当你用调试器（如 gdb）调试一个进程时，在使用断点中断进程后，进程就会变成跟踪 状态，这其实也是一种特殊的暂停状态，只不过你可以用调试器来跟踪并按需要控制进程 的运行。

# 进程S状态
## 介绍
**S** 是 `Interruptible Sleep` 的缩写，也就是可中断状态睡眠，表示进程因为等待某个事件（比如等待socket连接、等待信号量） 而被系统挂起。这些进程的`task_struct`结构被放入对应事件的等待队列中。
当进程等待的事件发生时（由外部中断触发、或由其他进程触发），对应的等待队列中的一个或多个进程将被唤醒，它会进入 R 状态。


# 进程D状态
## 介绍
**D** 是 `Disk Sleep` 的缩写，也就是**不可中断状态睡眠（`Uninterruptible Sleep`）**，一般 表示==进程正在跟硬件交互，并且交互过程不允许被其他进程或中断打断==。

## 为什么需要D状态

 `uninterruptible sleep` 存在的意义就在于，内核的某些处理流程是不能被打断的。如果响应异步信号，程序的执行流程中就会被插入一段用于处理异步信号的流程（这个插入的流程可能只存在于内核态，也可能延伸到用户态），于是原有的流程就被中断了。
 在对某些硬件进行操作时（比如进程调用`read`系统调用对某个设备文件进行读操作，而`read`系统调用最终执行到对应设备驱动的代码，并与对应的物理设备进行交互），可能需要`uninterruptible sleep`状态对进程进行保护，以避免进程与设备交互的过程被打断，造成设备陷入不可控的状态。
 
 即：**不可中断状态(`D`状态)，表示==进程正在跟硬件交互==，为了保护进程数据和硬件的一致性，系统不允许其他进程或中断打断这个进程**。
 例如对某些硬件设备进行操作时刻（等待磁盘Io,等待网络io、其他外设 IO等等）。


进程在等待 I/O 操作时进入不可中断的睡眠状态 (D 状态) 是由于以下几个原因：
 **(1) 确保数据一致性和完整性**：
当进程正在进行重要的 I/O 操作时，例如读取或写入磁盘数据，确保数据的一致性和完整性至关重要。如果进程在等待 I/O 操作完成时被中断，可能会导致数据不一致或损坏。因此，进程被放入不可中断的睡眠状态，以避免被信号中断。

**(2) 硬件依赖性**：
一些 I/O 操作是直接与硬件设备交互的，例如磁盘读写、网络数据传输等。
这些操作往往需要等待硬件设备完成相应的任务，而硬件设备的响应时间是不可预知的。将进程放入不可中断的睡眠状态，可以确保在等待硬件设备响应期间，进程不会被其他操作干扰。

 **(3) 减少上下文切换开销**：
不可中断的睡眠状态可以减少上下文切换的开销。在这种状态下，内核不会尝试频繁地唤醒和调度该进程，这样可以减少不必要的上下文切换，优化系统性能。

**(4) 防止资源竞争**
当进程在等待某些关键资源时，例如文件系统锁、内存分页等，不可中断的睡眠状态可以防止资源竞争和死锁情况的发生。这样可以确保系统在处理这些关键资源时的稳定性。


## D状态产生的原因

处于`uninterruptible sleep`状态的进程通常是在**等待IO，比如磁盘IO，网络IO，其他外设IO**。
**进程处于D状态一般情况下很短暂，不应该被top或者ps看到**。

如果进程正在等待的`IO`在较长的时间内都没有响应，那么就很会不幸地被`ps`看到了（即：进程在top和ps看到长期处于D状态），同时也就意味着==很有可能有`IO`出了问题，可能是外设本身出了故障，也可能是比如挂载的远程文件系统已经不可访问了==（由`down`掉的`NFS`服务器引起的`D`状态）。

### 潜在原因
在 Linux 中，长期处于 D（Uninterruptible Sleep）状态的进程通常是由于以下原因之一：

**I/O 操作**：
进程正在等待某个 I/O 操作完成，例如读取磁盘数据或网络操作。这是最常见的 D 状态原因之一。
- 等待磁盘 I/O 完成：进程可能正在等待磁盘读取或写入操作完成。由于磁盘 I/O 操作通常需要较长时间，因此进程会进入不可中断的睡眠状态，直到 I/O 操作完成。
- 等待网络 I/O 完成：进程可能正在等待网络数据的接收或发送。

**文件系统操作**：
进程可能由于文件系统问题而无法继续执行，例如等待文件系统锁定或未处理的文件系统错误。
- 等待文件系统锁：进程可能正在等待获取文件系统的某个锁，以便进行文件操作。
- 文件系统的同步操作：例如，`sync` 操作可能会导致进程进入 D 状态，直到所有缓冲区数据都写入磁盘。

**内存管理(内存不足)**:
- 等待内存分页：如果系统内存不足，进程可能需要等待内存分页操作完成。
- 等待内存交换：在使用交换空间的情况下，进程可能需要等待交换操作完成。

**同步原语**：
- 等待互斥锁或信号量：进程可能正在等待其他进程释放某个互斥锁或信号量。

**硬件设备或驱动问题**：
- 等待硬件设备响应：进程可能正在等待某个硬件设备的响应，例如等待硬件驱动程序完成某个操作。
进程与设备驱动程序之间可能存在问题或者硬件存在问题（比如磁盘故障），导致进程无法正常完成操作并进入睡眠状态。

**内核 Bug**：
某些情况下，进程可能在内核中遇到 Bug 或其他异常情况，导致无法正常恢复。

### 低内存状态造成大量进程进入D 状态的情况

在低内存状态下，大量进程进入 D 状态（不可中断的睡眠状态）通常是由于**内存管理**和 **I/O 操作**等待所引起的。
这可以通过查看 Linux 内核的内存管理和 I/O 子系统的源码来理解。

#### 内存管理和页回收

当系统处于低内存状态时，内核需要回收内存页，以便为新的内存分配请求提供足够的可用内存。
这个过程涉及页回收 (page reclaim) 和交换 (swap) 操作。内存管理部分的主要相关源码位于 `mm/vmscan.c` 和 `mm/swap.c`。

##### 页回收过程
在 `mm/vmscan.c` 中，函数 `shrink_node()` 和 `shrink_zone()` 会被调用来回收内存页。当内存不足时，这些函数会尝试将不常用的页面从内存中移除，写入交换空间，或释放内存。
以下是一个简化的代码示例：
```c
static void shrink_node(pg_data_t *pgdat, struct scan_control *sc)
{
    // 尝试回收内存页
    for_each_evictable_lru(lru) {
        shrink_list(lru, pgdat, sc);
    }
}

static void shrink_zone(struct zone *zone, struct scan_control *sc)
{
    // 尝试从特定的内存区域回收页
    for_each_evictable_lru(lru) {
        shrink_list(lru, zone, sc);
    }
}

```

##### swap交换操作
当需要将页面交换到磁盘时，涉及的函数通常位于 `mm/swap.c`。这些函数会将内存页面写入交换磁盘设备。这个过程可能会导致进程等待磁盘 I/O 操作完成，从而进入不可中断的睡眠状态。例如，函数 `__swap_writepage()` 会被调用来执行交换操作：

```c
int __swap_writepage(struct page *page, struct writeback_control *wbc)
{
    // 将页面写入交换设备
    // 如果交换操作需要等待磁盘 I/O 完成，进程将进入 D 状态
}
```

#### 文件系统和 I/O 操作
在低内存状态下，进程可能会因为等待`I/O` 操作而进入 `D` 状态。这是因为内核需要将脏页面（`dirty pages`）写回磁盘，以释放内存。
文件系统和块设备 `I/O` 的相关源码位于 `fs/` 和 `block/` 目录中。

##### 文件系统写回

当需要将脏页面写回磁盘时，文件系统会调用 `writeback` 机制。相关代码位于 `fs/fs-writeback.c`。
函数 `writeback_single_inode()` 和 `__writeback_single_inode()` 会被调用来写回脏页面：
```c
static int __writeback_single_inode(struct inode *inode, struct writeback_control *wbc)
{
    // 将脏页面写回磁盘
    // 如果磁盘 I/O 操作需要时间，进程将进入 D 状态
}

```

## D状态的理解
`uninterruptible sleep`状态的进程与`Interruptible Sleep`状态类似，进程处于睡眠状态，但是此刻进程是不可中断的。
**进程的D状态，不可中断，指的是进程的不可中断睡眠，并不是CPU不响应外部硬件的中断，而是指进程不响应异步信号**。

==D状态的进程是不可中断睡眠，无法响应异步信号（比如通过Kill 发送的信号），此时进程是释放了CPU，CPU此时是可以响应硬件中断的==。

### D状态和S状态的区别

绝大多数情况下，进程处在睡眠状态（`Interruptible Sleep` ）时，总是应该能够响应异步信号的。因此，通过`kill` 发送**异步信号**，是可以杀死一个处于`S`状态的进程。

但是处于`D`状态的进程，无法响应异步信号，无法通过`kill`命令杀死。

## D状态的危害
### 对系统以及其他进程的危害
长期处于 `D` 状态的进程在**一般情况下并不会对系统造成直接的危害**，因为它们**不占用 CPU 资源**。
一般情况下，也不会影响其他正常运行的进程，但是如果`D`状态的进程占用某个共享资源不释放，可能会影响其他的进程。

### 对自身服务的危害
然而，长时间处于 D 状态可能会导致以下问题：
**资源占用**：
这些进程仍然在占用系统资源，如内存和进程表项。如果大量进程长时间保持在 D 状态，可能会导致系统资源的耗尽。
    
**响应性降低**：
如果关键的系统任务或操作需要等待长时间处于 D 状态的进程完成，可能会导致系统的响应性下降。
    
**调试困难**：
由于长时间处于 D 状态的进程无法被中断，对于开发人员来说，诊断和调试这些进程可能会更加困难。
    
**潜在系统稳定性问题**：
长时间处于 D 状态的进程可能暗示系统中存在硬件故障、设备驱动程序问题或内核 `Bug`。这些问题可能对系统的稳定性产生潜在影响。

如果系统中出现大量处于长时间 D 状态的进程，建议进行系统故障排查，并尽快解决引起这些问题的根本原因。这可能涉及检查硬件、设备驱动程序、文件系统以及相关的内核配置和补丁。

## D状态进程的特性
### 无法使用Kill -9杀死 
**处于D状态的整个进程无法被`kill -9` 掉**；

`kill -9` 只是给进程发送了一个 `SIGKILL` 信号，当一个进程处于D状态时（信号处理，或者系统调用中）会无法处理任何信号，包括 `SIGKILL` 也不能被正确处理，导致进程不能被立即杀掉，也就是我们常说的 D 状态（不可中断的睡眠状态）。

#### 杀死D状态进程的父进程
如果父进程被成功杀死，所有由该父进程创建的子进程（包括处于D状态的进程）可能会受到影响。操作系统通常会将这些子进程的父进程设置为`init`进程（PID为1），以确保它们能够继续运行。

处于D状态的子进程会变成“孤儿进程”，由`init`进程接管。这意味着这些子进程的父进程不再存在，但它们仍然会继续等待原本的事件。

如果父进程在被杀死时持有某些资源（如文件描述符、内存等），这些资源可能会被操作系统释放。

即：**杀死D状态的进程的父进程，感觉其实对于D状态的进程是没有任何影响的，还是在等待资源。只不过是换了个父进程**。

### 无法使用pstack和strace

处于D状态的整个进程，很多常用的调试工具，比如 `strace`, `pstack` 等也都失灵了。
 `strace`、`pstack` 一般也是利用发送某个特殊的信号给进程来实现的，在这种状态下也是无法使用。

**堆栈查看**
此时可能无法使用`pstack` 查看堆栈，Linux 下提供了`procfs`（就是 Linux 下的 `/proc` 目录）, 通过它就可以看到任何一个进程的当前内核调用栈。

### 无法使用GDB调试
D (`uninterruptible sleep`)，不可中断的睡眠状态 ，此时进程不能被信号唤醒，GDB等调试工具也不能对它调试，因为GDB也是用到了信号。

## 杀死D状态的进程

### 方法一：重启reboot

D (`uninterruptible sleep`)，不可中断的睡眠状态的进程，无法使用`Kill` 杀死。

### 方法二：解决IO阻塞的问题
处于`uninterruptible sleep`状态的进程通常是在等待`IO`，比如磁盘`IO`，网络`IO`，其他外设`IO`，如果进程正在等待的`IO`在较长的时间内都没有响应，就会转变成为`D`进程。此时只要解决引起`io`阻塞的问题进程状态通常会回归正常。


### 方法三：修改内核，将其进程状态转化为别的状态，然后kill掉

1. 创建目录kill_D_process，进入目录继续
2. touch killd.c,写入如下内容：
```c
#include <linux/init.h> 
#include <linux/kernel.h> /*Needed by all modules*/
#include <linux/module.h> 
#include <linux/sched.h> //for_each_process 

MODULE_LICENSE("BSD"); 
static int pid = -1; 
module_param(pid, int, S_IRUGO); 
static int killd_init(void) 

{ 
    struct task_struct * p; 
    printk(KERN_ALERT "killd: force D status process to death/n"); 
    printk(KERN_ALERT "killd: pid=%d/n", pid); 
    //read_lock(&tasklist_lock); 
    for_each_process(p){ 
        if(p->pid == pid){ 
            printk("killd: found/n"); 
            set_task_state(p, TASK_STOPPED); 
            printk(KERN_ALERT "killd: aha, dead already/n"); 
            return 0; 
        } 
    } 

    printk("not found"); 
    //read_unlock(&tasklist_lock); 
    return 0; 
} 

static void killd_exit(void) 
{ 
    printk(KERN_ALERT "killd: bye/n"); 
} 

module_init(killd_init); 
module_exit(killd_exit); 
```

3. touch Makefile 文件，写入：
```bash
obj-m := killd.o
```

4. 执行如下命令。生成一堆文件，其中有文件killd.ko。
```bash
# 必须存在内核的`kernel-header`, `kernel-devel` 源码 
make -C /usr/src/kernels/2.6.32-754.23.1.el6.x86_64/ M=`pwd` modules
```

获取内核的`kernel-header`, `kernel-devel`
```bash
yum install kernel-header 
yum install kernel-devel
其中kernel-devel将内核源代码安装到/usr/src/kernels/目录下 

或者

查看内核版本: uname -r
下载新内核源码：到官网www.kernel.org，下载最新版本linux内核，保存到/usr/src/kernels目录
```


5. 找到处于D状态的进程，比如pid=1234，执行如下命令，进程状态变成T(停止状态)，然后使用`kill -9 pid`杀死
```bash
sudo insmod ./killd.ko pid=1234
```


## D状态进程的恢复
正是因为得不到`IO`的相应，进程才进入了`uninterruptible sleep`状态，所以要想使进程从`uninterruptible sleep`状态恢复，就得使进程等待的IO恢复。
比如如果是因为从远程挂载的`NFS`卷不可访问导致进程进入`uninterruptible sleep`状态的，那么可以通过恢复该NFS卷的连接来使进程的IO请求得到满足。


# 系统中出现大量的D状态和Z状态进程的分析
## (1) dstat查看系统的IO以及cpu使用情况
那么什么工具可以查询系统的 I/O 情况呢？这里推荐使用 **dstat** ，它的好处是，可以同时查看 CPU 和 I/O 这两种资源的使用情况，便于对比分析。

```bash
# 间隔1秒输出10组数据
$ dstat 1 10
```
![](attachments/Pasted%20image%2020241218141326.png)

可以看到，每当 iowait 升高（wai）时，对应的磁盘的读请求（read）都会很大。这说明 iowait 的升高跟磁盘的读请求有关，很可能就是磁盘读导致的。

## (2) top查看处于D状态的进程

那到底是哪个进程在读磁盘呢？再次关闭并重启应用，top 观察下输出情况。  
![](attachments/Pasted%20image%2020241218141037.png)

重点关注下 D 状态的进程，因为它们可能在等待 I/O。

## (3)  pidstat 查看进程磁盘读写

### 指定进程的IO情况
`dstat` 可以看到的是整个系统的IO的情况，无法查看某个进程的`IO`的情况。

```bash
# -d 展示 I/O 统计数据，-p 指定进程号，间隔 1 秒输出 3 组数据
$ pidstat -d -p XXX 1 3
```
![](attachments/Pasted%20image%2020241218140802.png)

可以看到，这两个进程目前并没有任何磁盘读写。那要怎么知道，到底是哪个进程在进行磁盘读写呢？

### 所有进程的IO情况
继续使用 pidstat，这次观察所有进程的 I/O 使用情况，如下：
```bash
# 间隔 1 秒输出多组数据 (这里是 20 组)
$ pidstat -d 1 20
```
![](attachments/Pasted%20image%2020241218141800.png)

可以发现，是 app 进程在进行磁盘读，并且每秒读的数据有 320 MB，看来就是 app 的问题。

## (4) strace 跟踪进程系统调用
不过，app 进程到底在执行啥 I/O 操作呢？这里，注意进程用户态和内核态的区别，进程想要访问磁盘，就必须使用系统调用。

strace 是常用的跟踪进程系统调用的工具。可以用 -p 参数指定 PID 号：
```bash
strace -p 6680
```

![](attachments/Pasted%20image%2020241218142004.png)

图中，提示 strace 命令执行失败，没有权限。其实本身就处于 root 用户，不应该没有权限的。一般遇到这种问题时，先检查一下进程的状态是否正常。

```bash
ps aux | grep 6680
```

![](attachments/Pasted%20image%2020241218142036.png)

可以看到，进程 6680 已经变成了 Z 状态，也就是僵尸进程。僵尸进程都是已经退出的进程，所以就没法继续分析它的系统调用。

## (5) perf 分析系统 CPU 时钟事件
至此，发现 top、pidstat 工具无法给出更多信息。这时，可以求助那些基于事件记录的动态追踪工具，比如 perf。

```bash
# 记录性能事件，等待大约15秒后按 Ctrl+C 退出
$ perf record -g

# 查看报告
$ perf report
```

![](attachments/Pasted%20image%2020241218142209.png)

图中的 swapper 是内核中的调度进程，可以先忽略掉。

可以发现， app 的确在通过系统调用`sys_read ()` 读取数据。并且从 `new_sync_read` 和 `blkdev_direct_IO` 能看出，进程正在对磁盘进行直接读，也就是绕过了系统缓存，每个读请求都会从磁盘直接读，这就可以解释我们观察到的 `iowait` 升高了。

找到了问题的根源，那么可以从代码层面，看是否能找到 **直接 I/O** 的操作？

由于 app 是经过编译后的 C 应用程序，所以还是直接看下课程提供的 C 源码 ，具体调用位置如下：
```c
// O_DIRECT 选项打开磁盘，于是绕过了系统缓存，直接对磁盘进行读写。
int fd = open(disk, O_RDONLY | O_DIRECT | O_LARGEFILE, 0755);
```

## (6) 优化 iowait 问题
直接读写磁盘，对 `I/O` 敏感型应用（比如数据库系统）是很友好的，因为你可以在应用中，直接控制磁盘的读写。

但在大部分情况下，我们最好还是通过系统缓存来优化磁盘 `I/O`，换句话说，删除 `O_DIRECT` 这个选项就是了。
