# bilibili的内网dns
## 内网DNS
### 涉及的概念
#### 权威 Name Server
权威 Name Server 是实际持有并负责特定域(zone)资源记录（RR）的服务器，通常是解析器查找 IP 地址过程中的最后一步，拥有这些域的最终解释权。

权威 Name Server 在软件层的实现又可以分为主权威和从权威。对 DNS 查询来说主从权威完成是对等的，但是它在软件架构上提供了必要的故障灾备和横向扩容能力。
　　
#### 解析器(Caching Name Servers)

![](attachments/Pasted%20image%2020250124162616.png)

解析器通常是 DNS 查询中的第一站，处理用户的递归查询，并提供完整的答案。

当收到请求时，解析器向DNS层次结构发出一个或多个迭代查询。在获得一个完整的答案(或一个错误)后，解析器将答案传递给用户，并将记录放入其缓存。用户对同一查询的后续请求将从解析器的缓存中得到回答，直到缓存记录的TTL过期，那时它将从缓存中被删除。请求相同信息的下一个用户查询将导致对DNS层次结构的一系列新的查询。

**解析器**在不同的使用场景下常被称为各种令人困惑的名字，如**缓存名称服务器**、**递归名称服务器**、**转发解析器**、**区域解析器**和**全面服务解析器**等。

### 优点
以 DNS 为基础的内网 DNS 服务则提供了一些额外的好处：

#### 私有域名
（1）方便内网服务互联互通
（2）外界无法感知和探测到，满足了安全性和隐私方面的需求

#### 外网DNS劫持
（1）拦截特定公网域名到内网 ip，降低公网带宽和访问延迟。
如某核心服务 A 早期只有公网域名，随着业务发展，内部非常多其他服务调用 A 服务，此时内部调用产生的公网带宽成本已非常高。
而推动其他服务更换内网域名成本不低，DNS 劫持则能轻松帮我们解决问题。

（2）拦截恶意公网域名，降低安全隐患

#### 极低的解析延迟以及极高的吞吐量
内网DNS，可以减少DNS请求的链路，降低时延。

#### 方便运维管理
内部调用 API，方便管理与运维
主机名管理和私有ip反向解析支持
支持特定域转发


## 架构演进
### 第一代 DNS 架构
![](../attachments/Pasted%20image%2020240126120837.png)

**（1）架构**
B 站内网 DNS 服务早期第一代架构相对比较简单，**核心关注高可用和稳定性，采用了主从模式**。
保障每个核心 IDC 有独立的从权威集群，通过 VIP 提供负载均衡，并通过 VIP 健康检查机制自动踢掉故障节点。同时各 IDC 机房内网互通，互为备份。

**（2）缺点**
随着业务的发展，在高 QPS 场景中，==主从权威 Zone 配置同步时存在解析时长突增，响应时延不稳定的问题==。其次从权威的可扩展性也相对较弱。因此我们衍生出第二代 DNS 架构。

### 第二代 DNS 架构
![](../attachments/Pasted%20image%2020240126121011.png)

**（1）架构**
第二代 DNS 架构主要引入了==多级缓存==。

<1.1> 首先是引入了 Caching Name Servers，可扩展性得到了非常大的提升。==同时也避免了权威节点配置/Zone变更带来的dns查询时延的抖动。==
```text
缺点：
	内网的记录变更，那么cache中存在缓存，可能无法及时生效。对于这种情况，可以考虑延迟生效，即cache中的缓存只创建不刷新，超时删除后后期通过新的dns请求来重新来触发重新生成cache。

```

<1.2> 其次是针对大数据、AI 等 QPS 极高的业务，引入 NSCD 作为 Client 缓存服务。
```bash
优点：
	既降低了响应延迟也提高了整体服务吞吐。
```

**(2) bind9 版本升级**
在此基础上，第二代架构还对 BIND9 Server 进行了升级和优化。
BIND9 虽然支持多线程，但是在我们早期使用的 `9.11` 版本中，单实例 `QPS` 峰值在 10 万左右。在新的版本中，因为支持 `reuseport`、日志写缓存等新特性，对性能有非常大提升，单实例可以充分利用多核 CPU，在生产环境压测中单机 `QPS` 超过 `150 万`，因此我们也在线上进行了升级。

### cache服务器实现详解
#### 方案
可以考虑使用 DPDK 实现一个 `Fullnat` 的 `DNS cache`。

**(1) 首先基于sip + 域名进行`hash`，查询缓存**

缓存中如果存在多个记录，则随机打乱顺序返回记录。
注：基于`sip`+ 域名进行`hash`，是考虑了智能查询。

**(2) `cache`设备中查询不到缓存结果，则进行`fullnat` 转发到内网 DNS服务器**
`Fullnat` 而不是`Dnat`，是因为 内网`dns server`的响应需要返回给同一个`cache`设备，进行保存。
因此，需要在内网的`dns`服务器上进行`snat`，还原`dns`请求原始的`client ip`，就不是目前的 `TOA/UOA` 这种 `hook 系统调用，比如getsockopt` 的方式，而是真正的`nat`地址转换。

**(3) DPDK 实现一个 `Fullnat` 的 `DNS cache`提供健康检查**
类似于 一个 `VS`下，存在多个`RS`。`RS`就是内网`DNS` 的`Slave`服务器。
`VS` 就是 `DNS Cache` 对外提供的服务。
如果某个内网DNS服务器在版本升级，下线，或者服务挂掉，那么健康检查失败，后续的DNS查询就不会转发给这个服务器了。

#### 拓展
**（1）Fullnat DNS Cache 给 后端DNS转发时，什么情况下添加`cip, cport`这些信息？ 如果后端DNS服务器下线，或者服务挂掉怎么办？**

应该也不用考虑这个问题，只要是转发给后端的`DNS`服务器的报文，都是携带有`CIP:CPort`信息的。
如果`cache`服务器中存在缓存，则直接给请求拦截了，到不了后端`DNS`服务器。
后端DNS服务器的`UOA/TOA`中的表项，也应该不用太多的管理。

**（2）Cache 服务器中的域名缓存记录，以及conn表信息提升可观测性**
目前的bind9，基本上没有基于连接的日志信息。如果实现一个 `Fullnat` 的 `DNS cache`，可以考虑打印更多的日志信息，统计信息。

`cache` 服务器的 `conn`信息，可以对应 后端DNS服务器的请求信息。也可以知道查询了哪些域名，以及域名的响应时间等，可能比 bind9 中的日志信息更加详细。
注：此时 会话`conn`的`key`，可能是域名的类型 + 域名的名称 + DNS请求的源`ip`。即：会话的 `conn`，和缓存记录的`key`其实是一样的，是对应的。

**(3) 缓存的key的问题，缓存的数量的问题**
基于`sip`+ 域名进行`hash`，这样可能导致一个集群中的不同Client请求，都会对应不同的缓存。那么缓存的数量就会太多。
如果是目前的每个集群都有部署`cache`服务器，那么是否也不需要`SIP`了，这样可以节省大量的缓存，但是这样就限制了 `cache`服务器的部署，以及业务不可以跨集群访问`cache`服务器。
更好的是，每个View都有基于域名的cache。`View`就是`Acl` 网段。`Cache` 服务器收到一个`DNS`请求后，先基于`SIP`查询`ACL`，得到所属的`View`，然后在这个`View`中来基于域名来查询`Cache`。

**(4) 泛域名的问题**
对于泛域名，其实从缓存中是无法识别，缓存中看到的是具体的域名。

**(5)缓存的清理问题**
需要支持清理特定的域名的缓存，特定`zone`相关的缓存，特定view下的缓存。

**(6)外网的域名怎么处理？**
对于外网的域名的查询。DNS的查询流程是：
```bash
先经过Cache 服务器，查询不到----> 
DNS内网服务器，查询不到，向`forwarder`转发----> 
经过SNAT服务器(`SIP`为`SNAT`的外网`IP`，`DIP`为外网的`Forwarder-IP`) -----> 
外网`forwarder`； 
```
对于外网`Fowarder`来说，`DNS`智能解析时，看到的`SIP`其实是`SNAT`的外网`IP`，但是由于`SNAT`每个机房都存在，`SNAT`的外网`IP` 就可以代表 `Client` 所在的 区域。因此，此时外网 `Forwarder` 返回的 智能解析的结果，是正确的。

那么，对于外网域名的查询结果，按照`View`进行保存，是基于`client`的内网`IP`来匹配`View`的`ACL`，其实也是合理的。
因为，不同`IDC`机房，对应的`SNAT`的外网`IP`网段是一一对应的，不同的`IDC`机房的内网的网段也是一一对应的。

**(7) dns 缓存需要 Cname, A记录，4A记录，以及反解**
如果一个域名存在`Cname`，DNS后端服务器响应的时候，需要存储 域名和 `Cname`的缓存记录。
接下来，再基于`Cname`进行A记录的查询, 需要保存 `Cname`和`A`记录的关系。

**(8) TCP的dns查询如何处理？**
默认使用的是`UDP`进行`DNS`查询，如果`DNS`响应的长度超过了`512`，则`DNS`回复会设置截断标识(`TC=1`), 然后进行`TCP`的三层握手以及`TCP`的`DNS`请求以及响应。
也就是说：想要获取`TCP`的`DNS`请求的域名，那么需要先三次握手。
因此，对于`TCP`而言，不进行缓存，`inbound`和`outbound`方向都是直接转发即可。因为`TCP`进行缓存也没有用。下次的`TCP`请求，还是要先三次握手之后才可以看到`DNS`请求。那么，无论是`TCP`的三次握手还是`TCP`的`DNS`请求报文都进行转发即可。
这个就涉及到内网`DNS`服务器上，也需要进行安装`TOA`，进行`NAT`而非`Hook`的方式还原真实的`Client-IP`。

**(9)不同的DNS后端服务器支持不同的Zone**
对于容器场景下，不同的集群的`service`服务以及`pod-name` 对应的 `zone` 不一样，每个集群都有 自身的`coredns`集群负责本集群的 `pod` 以及  `service`  域名的解析。
如果一个集群中的`Pod`需要访问其他集群的`Sevice`域名，以及进行反解，那么按照`core-dns`，目前可能无法做到跨集群进行解析。

思路：可以考虑，利用 `cache-dns` 进行中转，基于`zone`的信息， 将`DNS`查询中转到特定集群的`CoreDns`进行解析。

那么， 通过`ipvsadm`来查看`cache-dns` 的`VS、RS`以及`RS管理的zone`的形态，可能就是：
```bash
之前的形态，可能是：
# ipvsadm -ln 
TCP  192.22.2.57:8888 wlc conn_timeout 120
  -> 192.20.22.1:80               FullNat 10     0          0
TCP  192.22.2.57:80 wlc synproxy conn_timeout 12
  -> 192.20.22.1:80               FullNat 10     0          0

之后的形态，可能是：
# ipvsadm -ln 
TCP  192.22.2.57:8888 wlc conn_timeout 120
  -> 192.20.22.1:80               FullNat 10 
	  -> view: Container-Cluster1 # 容器集群1
		  -> zone: service-prefix1-Container-Cluster1 # 集群1下管理的service的前缀
		  -> zone: service-prefix2-Container-Cluster1
		  -> zone: service-prefix3-Container-Cluster1
	-> 192.20.22.2:80               FullNat 10 
	  -> view: Container-Cluster2 # 容器集群2
		  -> zone: service-prefix1-Container-Cluster2
	-> 192.20.22.3:80               FullNat 10 # IDC的内网DNS的anycast IP
	  -> view: bjx # 
		  -> zone: ALL # 
	  -> view: bjy # 
		  -> zone: ALL # 
	  -> view: default # 除了其他的view，剩余的网段都匹配default view
		  -> zone: ALL # 

注：可能一共就只有一个`VS`，RS就是内网的DNS集群的`anycast IP` 以及各个集群的`Core-dns`的`Anycast IP`，或者具体的`DNS`设备/`core-dns`的设备，这样可以利用健康检查。

注：其实上面，通过`ipvsadm`来查看，先`RS`，然后`View`，再是`Zone`，也不一定好。因为层次关系的顺序不好。
其实通过`json`格式来展示，可能层次关系，更清晰一些。但是`json`格式的可读性不太好。
```

上面只是显示的布局，程序内部的数据结构的组织，可能不是这样的。

==整体的流程==：
```text
(1) dns的请求到达`cache`服务器，基于`sip`，来查询 `View`。
如果是来自于`IDC`的`client`的请求，就可以匹配到某个`IDC`的ACL网段。
如果是来自于容器的请求，就可以匹配某个容器的ACL网段。

(2) 如果是容器的`dns`请求，得到`VIEW`后：
2.1> 在这个View中 基于域名查询 Cache，如果可以查询到，直接返回。
2.2> 查询不到，则基于要查询的域名，得到对应的 域名对应的 Zone，然后在这个 Zone下选择RS(即选择 coredns 服务器)，然后进行 Fullnat 转发给选择的coredns 服务器。

(3) 如果是`IDC`的`dns`请求，得到`VIEW`后：
3.1> 在这个View中 基于域名查询 Cache，如果可以查询到，直接返回。
3.2> 如果查询不到：则基于要查询的域名，得到的默认的`ALL-Zone`。然后在这个 `ALL-Zone`下选择RS(即选择后端DNS服务器)，然后进行 `Fullnat` 转发给选择的后端 `DNS` 服务器。

```


## 监控统计
`DNS` 服务监控告警主要分为三个层面：
1. 服务器的主机层
2. `DNS`业务层
3. `Client` 端

### 服务器的主机层
主机层通常都会有 `CPU`、内存、网络、磁盘等资源的使用率、饱和度、错误监控告警。这里主要强调两点容易忽略或者对 DNS 服务比较重要的监控告警。

- 单核`CPU`/单网卡的使用率告警
现代 IT 服务架构中，从交换机到服务器网卡到服务器`CPU`，各个路径几乎都是多 `Pipeline` 负载均衡，因为错误配置或使用不当，可能会出现单核CPU/单网卡负载不均衡，引发服务异常的情况。

- 网络层面
1. 网卡收发包异常告警
2. `TCP、UDP errors （InError, OutError, RecvBuffErr, SendBuffErr）` 告警


### DNS业务层
- BIND 内部指标采集BIND 通过 statistics-channels 暴露了丰富的内部监控指标。
早期我们通过 bind_exporter 采集，但是遇到两个比较明显的问题：一是 bind_exporter 默认会采集 /xml/v3/tasks 数据，这个路径下的数据即无用，又会严重影响解析时延；二是部分比较重要的指标 bind_exporter 没有采集。因此我们重新开发了采集程序。
- Zone 记录值变化率/变化量告警监测每个 Zone 的记录值变化量，防止内部 API 等异常变更导致大量记录值被删除。
- BIND 错误日志监控告警错误日志能更详细的反应 BIND 内部的异常情况，帮助我们及时排障。

### Client 端探测告警
服务内部的监控并不总能真实反映用户到服务端的访问质量，因此我们在各个机房部署多个探针，模拟真实用户请求，多Zone多域名高频率监测每个 Server 的可用性、内容正确性和响应时延。

Client 探针多次帮助我们及时发现网络设备小概率BUG、网络拥塞等业务方还感知不到的异常。
同时增加 Client 到 Server 的网络 Ping 时延和丢包率监控，在异常时做辅助判断。
这里补充一点，公网公共 DNS 也并不是稳定的，需要对其进行监测和告警。目前我们的实践经验是阿里云公共 DNS 稳定性相对更好一些。

## 注意事项

### 保障 UDP 和 TCP 端口用户皆可访问

通常 DNS 默认使用 UDP 传输，同时在 rfc 中约定 DNS 使用 UDP 传输时，包体需小于等于 512 字节(不包括 IP 或 UDP 包头)。512 字节的限制在大部分场景都能满足需求，但当记录值过长超过限制时，Server 端需置 TC 位为 1，告知 Client 响应被截断。Client 在收到 TC 位为 1 的响应时，需用 TCP 重新发起请求。这就要求 TCP 端口也必须可达。

根据以上信息，也额外提醒大家，在选域名时应尽量短小，记录值尽量简单，以便提高解析速度。

### Zone 配置变更后必须增大序列号

主从权威的同步过程如下：
① 主节点 `Zone` 配置变更，向从节点发送 `NOTIFY` 通知
② 从节点返回 `NOTIFY Respons`，并向主节点发起 `SOA` 查询
③ 主节点返回 `SOA Respons`
④ 从节点对比 `SOA Respons` 中的序列号是否比自身序列号大，仅当 `SOA Respons` 序列号大于自身序列号时才发起 `Zone transfer request`，并利用 `TCP 53` 端口进行数据传输

因此 `Zone` 配置变更后必须增大序列号，否则会导致主从节点数据不一致。


### 慎用 rndc flush 刷新全量缓存

线上难免会遇到刷新缓存的需求，如果直接用`rndc flush` 刷新全量缓存，在有客户端缓存如 `NSCD` 的情况下，在每一次客户端缓存过期的时间都可能会产生极高的 `QPS`。

因此，尽量使用 `flushname` 或 `flushtree` 来刷新指定域名或 `Zone`。

### 慎用泛域名解析
泛域名解析是指利用通配符 * 将所有的子域名都指向相同的解析记录，实现灵活配置。然而当某个子域名需要独立配置时，容易忽略泛域名的配置，引发故障。

举个例子(以真实故障为蓝本)，方便大家理解：
① 业务上线初期为了方便配置使用泛域名解析: `*.example.com CNAME xxxcdn.com`
② 发展一段时间后 `a.example.com` 有了新需求，需要加个 `TXT` 做验证
③ 运维同学添加解析 `a.example.com TXT xxx`
④ 此时因为 `a.example.com` 只有 `TXT` 记录，没有 `A/AAAA` 或 `CNAME`，直接导致 `a` 站点无法访问。
