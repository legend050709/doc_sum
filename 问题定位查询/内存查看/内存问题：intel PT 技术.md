# 传统perf record的不足

传统的性能分析工具，比如我们熟悉的perf record采样，就像是每隔几秒给程序拍一张快照，然后通过大量照片来猜测它到底干了什么。这种方法虽然开销小，但会丢失大量细节，尤其是那些转瞬即逝的“灵异事件”，比如偶发的卡顿、某次函数调用异常慢，在采样数据里很可能就找不到踪影。

而Intel PT的思路完全不同。Intel PT就像是给CPU装上了一台高精度的“行车记录仪”。它不“拍照”，而是**“录像”。它会以一种高度压缩的格式，近乎实时地记录下CPU执行过的每一条分支指令的走向**。是的，你没听错，是近乎每一条。通过记录这些分支（比如if-else跳转、函数调用call、函数返回ret），我们就能在事后像看电影回放一样，精确地重构出程序当时完整的执行流程。


# 介绍
Intel 处理器追踪（Intel Processor Trace，简称 PT）是 Intel CPU 架构中的一项硬件追踪技术，最早从第五代 Intel 酷睿处理器`Broadwell`开始支持。它旨在以极低的性能开销，记录 CPU 执行的指令流信息，为软件调试、性能分析和故障排查提供强大的支持。

与传统的基于采样的性能分析方法不同，Intel PT 记录的是精确的控制流信息，包括：

- 执行的指令地址
- 分支跳转的目标地址
- 时间戳信息

通过解码这些信息，可以完整地重建程序的执行轨迹，精确到每一条指令，这对于分析复杂的程序行为和定位偶发性问题非常有帮助。

所以，Intel PT的核心价值在于**事后分析和根因定位**。它特别适合用来分析那些**难以复现、间歇性发生的性能故障**。

# 特点
## 极低的开销
这项技术的核心价值在于其极低的开销（通常<5%）和高压缩比的数据格式；
在实际测试中，一个计算密集型工作负载运行7毫秒产生的PT数据仅约1MB，而解码后的指令流可达1.3GB。这种特性使得PT特别适合用于性能热点分析、复杂bug诊断以及安全审计等场景。



# PT 的支持

## 硬件支持

|CPU|Support|
|---|---|
|Broadwell (5th generation Core, Xeon v4)|More overhead. No fine grained timing.|
|Skylake (6th generation Core, Xeon v5)|Fine grained timing. Address filtering.|

## PT 和Linux支持
PT已经被集成到内核代码的工具包的perf里，可以简单的通过perf使用intel-pt。 当然还有一些其他的工具支持PT的比如VTune, gdb, JTAG debuggers.

|Linux version|Support|
|---|---|
|Linux 4.1|Initial PT driver|
|Linux 4.2|Support for Skylake and Goldmont|
|Linux 4.3|Initial user tools support in Linux perf|
|Linux 4.5|Support for JIT decoding using agent|
|Linux 4.6|Bug fixes. Support address filtering.|
|Linux 4.8|Bug fixes.|
|Linux 4.10|Bug fixes. Support for PTWRITE and power tracing|


基本上稍微新一点的内核都支持了PT。

# Intel PT能做什么

PT的强大之处在于，它不仅仅是记录“去了哪”，还能关联上**“什么时候去的”**。

**精确重构控制流**：这是PT的老本行。给你一个二进制文件（比如你的程序）和一份PT跟踪数据，工具就能告诉你程序到底执行了哪些指令，顺序是什么。这对于理解复杂的、条件分支繁多的逻辑，或者验证编译器优化是否正确，有奇效。

**时间戳与性能分析**：现代的PT还能定时插入“时间包”。虽然它不能给每条指令都打上精确到纳秒的时间戳（那样数据量就爆炸了），但它能以很小的粒度（比如每发生一次异步事件或每隔N个周期）记录时间信息。这样，你就能知道在重构出的指令流中，哪一段代码执行得慢。比如，你可以精确计算出自旋锁等待了多久，或者某个循环体单次迭代花了多少CPU周期。

**无限深度的调用栈**：传统的基于帧指针或调试信息的调用栈获取，在优化过的程序或者栈被破坏时可能会失效。而PT通过记录所有的call和ret指令，可以无损地重建出任意时刻的完整调用栈，而且深度没有限制（不像LBR只有最后32条）。这对于分析崩溃现场或者性能瓶颈的调用路径至关重要。

**与系统事件对齐**：因为PT数据流里包含时间信息，你可以把它和系统里其他事件（比如磁盘I/O完成、网络包到达）的日志在时间线上对齐，做关联分析。这对于诊断分布式系统中的端到端延迟问题非常有用。


# 使用场景
## 应用程序导致的尾时延
最初接触PT是为了排查一个线上服务的“幽灵”延迟问题。服务99.9%的时间响应都在10毫秒内，但总有那么0.1%的请求会莫名其妙地飙到100毫秒以上。
用常规的perf采样分析了无数次，热点函数都看烂了，就是找不到原因。最后上了PT，在问题发生时抓取了几毫秒的跟踪数据，解码后顺着指令流一步步“走”，终于发现罪魁祸首是一个很少触发的、涉及复杂锁竞争和内存屏障的代码路径。
